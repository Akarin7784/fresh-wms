## 1. 职责与边界
### 1.1 负责
1. 报损单 `scrap_order` / 报损行 `scrap_line`：建单、审批、过账（02 `post_out(SCRAP)`）、作废。
2. 报损来源：EXPIRY_SCAN、SELL_EXPIRED（按日）、MANUAL、RETURN_QC、RETURN_HANDOVER、COUNT、EXCEPTION、记账型 LIVE_DEATH / LIVE_SHRINK / PROCESS_LOSS，以及**本稿新增 `SUPPLIER_RETURN`**（第 10 篇退供超期未提）。
3. 对第 10 篇 `supplier_return` 的跨篇 ALTER：外键 `fk_srtn_scrap`、超期守卫 `trg_srtn_overdue`、反向唯一 `uq_srtn_scrap`（README 登记）。

### 1.2 不负责
冻结原语本身（02）；退供单的建立与提货（10）；财务损失核算（ERP）。

## 3. 领域模型
- 一张报损单对应一个来源（`uq_scr_source (source_type, source_id, source_date)`，驳回/取消的不计）。
- 冻结型来源在提交时 `hold(SCRAP_PENDING)`（source_type=SCRAP，source_id=报损单 id，operator_id=0），审批过账与解冻同事务；记账型不冻结、不出账。
- **SUPPLIER_RETURN**：source_id = `supplier_return.id`，原因固定 `PICKUP_OVERDUE`（`ck_scr_reason_src`：该原因只给这个来源）；冻结 op_key = `SRTO:{supplier_return.id}`（不是通用的 `SCRH:{scrap_line_id}`，由第 10 篇守卫按此键校验）。一张退供单永远最多一张报损单（`uq_scr_srtn`，不论状态）。

## 4. 涉及的表
### 4.1 `scrap_order`
本稿改动：`ck_scr_src_type` 加 `SUPPLIER_RETURN`；`ck_scr_reason` 加 `PICKUP_OVERDUE`；`ck_scr_reason_src` 加子句 `reason_code <> 'PICKUP_OVERDUE' OR source_type = 'SUPPLIER_RETURN'`；新索引 `uq_scr_srtn`。其余字段、状态守卫（`trg_scr_forward` 等）不变。
### 4.2 `scrap_line`
不变。
### 4.3 对第 10 篇 `supplier_return` 的 ALTER
| 对象 | 作用 |
|---|---|
| `fk_srtn_scrap`（PG；SQLite 触发器 `trg_srtn_scrap_fk`） | `scrap_order_id` 必须是真实报损单 |
| `trg_srtn_overdue`（PG，`SET search_path = pg_catalog, public, pg_temp`；SQLite `trg_srtn_overdue` / `_ins` / `_lock`） | 转 `OVERDUE_SCRAP` 只能自 `AWAITING_PICKUP`，且同事务已有：本篇报损单（SUPPLIER_RETURN / 本退供单 / PICKUP_OVERDUE / 未驳回取消）+ 该单下 HELD 的 `SCRAP_PENDING` 冻结（同库存行、量 = 退供量、op_key = `SRTO:{id}`）；超期后关键列只读 |
| `uq_srtn_scrap` | 一张报损单只挂一张退供单 |

## 5. 状态机
报损单状态机不变：DRAFT → PENDING_APPROVAL → APPROVED → POSTED，另 REJECTED / CANCELLED / VOIDED。SUPPLIER_RETURN 来源不属于锁定来源（K1），可驳回/取消；驳回或取消后**不能再开第二张**（`uq_scr_srtn` 不论状态占位，Doro 定），转第 10 篇异常单人工处理（10 §9）。

## 6. 核心流程
见第 10 篇 §6 时序图：报损单 INSERT → `hold(SCRAP_PENDING)` → 退供单转 `OVERDUE_SCRAP`，同一事务；之后按普通报损审批、`post_out(SCRAP)` 并释放冻结。

## 7. 接口清单与契约
超期转报损只由系统任务触发，不新增对外接口；`source_type=SUPPLIER_RETURN` 时详情带退供单号跳转。错误码对外映射已登记 00 §6.4（#2 第九轮）：`srtn_overdue_no_scrap_hold`、`srtn_scrap_not_awaiting`、`srtn_scrap_orphan` → 40930 ILLEGAL_STATE_TRANSITION；`srtn_overdue_immutable` → 40931 DOC_LOCKED。第 10 篇的 `srtn_temp_class_mismatch` → 40930（`detail.reason = SRTN_TEMP_CLASS_MISMATCH`）同表登记。

**本节 7.1 / 7.2 是 13 篇 §6.3-4 / §6.3-5 消费契约的后端定义**（字段名不改；13 篇表 1 里「09 已合 main，仍无接口清单」由此闭合）。公共约定：`X-Warehouse-Id` 必填并走 00 §6.4 三层校验；出参**数量字段一律是 DDL `*_milli` 的 3 位小数字符串**（00 §R2），金额是「分」的整数；分页一律 `{items[], next_cursor}`，游标不透明、只回传不解析。

### 7.1 效期预警（读）
前缀 `/api/v1/inventory`。

| 方法 | 路径 | 说明 | 权限点 |
|---|---|---|---|
| GET | `/api/v1/inventory/expiry` | 临期批次列表（按 `lot.sell_deadline`，越紧迫越前） | `inventory.expiry.view`（12 篇 §4.2） |
| GET | `/api/v1/inventory/expiry/{stock_id}` | 单条明细（同一 `items[]` 元素形状 + 库位与各项占用） | 同上 |

**列表入参**（13 §6.3-4 已定的名字照抄，服务端不改名）：
| 参数 | 类型 | 默认 | 语义 |
|---|---|---|---|
| `days_before` | int | 7 | 临期窗口：`sell_deadline ≤ 仓时区今天 + N 天`；`0` = 只看今天到期的；范围 `0–365`，越界 → 40001 |
| `zone_id` | bigint | 全部 | 只看该库区（`zone.id`，含温区） |
| `sku_id` | bigint | 全部 | 只看该 SKU |
| `include_sell_expired` | bool | `true` | `false` 时排除已过可售期（`sell_deadline < 仓时区今天`）的行 |
| `cursor` | string | — | 不透明游标 |
| `size` | int | 50 | 每页 `1–200`，越界 → 40001（13 未要求，本篇扩展） |

**列表出参**：`{items: [...], next_cursor: string|null}`，`items[]` 字段集 = 13 §6.3-4：
`{stock_id, sku_id, lot_code, expiry_date, sell_deadline, location_id, location_code, on_hand_qty, available_qty, days_to_expiry, sell_expired}`

- 数据源：直接 `stock ⋈ lot ⋈ location ⋈ zone`，**只带 `stock.on_hand_qty_milli > 0`**（长流复核 §7.1，本轮已改）。**不要用 `v_stock_available`**：`90_available_view.sql:32` 自带 `WHERE s.on_hand_qty_milli > 0 AND l.status = 'AVAILABLE' AND l.deleted_at IS NULL`，`l.status='AVAILABLE'` 会把**盘点锁定（`LOCKED`）库位**的临期货整行滤掉——08 篇建盘点单就是靠把库位置 `LOCKED`，于是「盘点期间的临期货在预警里查不到」。
- **为什么不能借用那个视图**：预警是**查询**语义（"现在什么快过期了"，LOCKED 也要看得见），"排除 LOCKED"是**分配**语义——02 §6 的 FEFO 是显式传参 `exclude_location_status=("LOCKED",)`（`02:897`）。两者不能共用一个视图。
- 已知边界（明示，不静默）：软删库位（`deleted_at IS NOT NULL`）理论上不该有在库行；若真出现，预警仍按 `on_hand_qty_milli > 0` 列出，由数据巡检告警，**不在这里静默隐藏**。
- 字段口径：`on_hand_qty` ← `stock.on_hand_qty_milli`；`available_qty` 在查询里写 `v_stock_available` 的**同一算式**（`on_hand − allocated − reserved − quality_hold − hold`，`90_available_view.sql:30`），保证与 13 §6.3-4 的 `available_qty` 逐字段一致。
- `days_to_expiry = sell_deadline − 仓时区今天`（可为负）；`sell_expired = sell_deadline < 仓时区今天`；两项都由服务端按仓库时区算，客户端不自行换算日期（13 §4.2 的日期口径）。
- **只见 `sell_deadline IS NOT NULL` 的行**：没有可售期口径的批次不进预警列表，免得把「未定可售期」显示成「不会过期」。
- 排序 `days_to_expiry ASC, stock_id ASC`；游标即该二元组（服务端编码），到底 `next_cursor = null`。
- 仓过滤按 `X-Warehouse-Id`；`zone_id` / `sku_id` 不属于本仓时**返回空列表**（不泄露存在性），不报 403。

**错误**：40001（`days_before` / `size` 越界、布尔值非法）、40311（`X-Warehouse-Id` 不在数据范围）、40401（`/expiry/{stock_id}` 库存行不存在或不属于本仓）。

### 7.2 报损单（读）
前缀 `/api/v1/scrap-orders`。

| 方法 | 路径 | 说明 | 权限点 |
|---|---|---|---|
| GET | `/api/v1/scrap-orders` | 列表 | `scrap.order.view`（12 篇 §4.2 明示即 13 篇原写的 `scrap.view`） |
| GET | `/api/v1/scrap-orders/{id}` | 详情：单头 + 行 + 冻结链接 | 同上 |

**列表入参**：
| 参数 | 类型 | 默认 | 语义 |
|---|---|---|---|
| `status` | string | 全部 | 逗号分隔多值；白名单 = `ck_scr_status` 的 7 个值，非法值 → 40001 |
| `source_type` | string | 全部 | 逗号分隔多值；白名单 = `ck_scr_src_type` 的 11 个值（含 `SELL_EXPIRED` / `LIVE_DEATH` / `LIVE_SHRINK` / `SUPPLIER_RETURN` / `PROCESS_LOSS`），非法值 → 40001 |
| `warehouse_code` | string | `X-Warehouse-Id` 所指 | 只允许本仓，跨仓 → 40311 |
| `created_from` / `created_to` | date | — | 按 `created_at` 的**仓时区日期**过滤，闭区间；`from > to` → 40001 |
| `cursor` / `size` | 同 §7.1 | | |

**列表出参**（= 13 §6.3-5 的单头字段集）：
`{items: [{id, code, source_type, source_id, source_date, reason_code, status, warehouse_id, created_at, posted_at}], next_cursor}`
排序 `created_at DESC, id DESC`。

**详情出参** = 列表单头字段 + `{work_date, amount_impact, applicant_id, approver_id, approved_at, void_approval_no, record_only, version, lines[], holds[]}`：
- `lines[]`：`{id, line_no, stock_id, sku_id, lot_id, scrap_qty, ledger_mode, hold_id, cost_amount}`（`scrap_qty` ← `scrap_qty_milli`）；
- `holds[]`：`{hold_id, hold_type, status, hold_qty, released_qty}`——13 侧用它渲染冻结行链接；`hold_id = 0`（已出库待报损、记账型来源）时该数组为空，前端不渲染链接；
- `record_only = true`（`PROCESS_LOSS` / `LIVE_DEATH` / `LIVE_SHRINK`）时 `holds[]` 恒空、且不显示「解冻」入口；
- 路径参数 `{id}` 接受数字主键或业务单号（`SCR-` 前缀按 `code` 解析），两者都做仓校验。

**错误**：40001（枚举 / 日期非法）、40311、**404 `40411 SCRAP_ORDER_NOT_FOUND`**（id / 单号不存在，或存在但不属于本仓——统一 404，不用状态码泄露跨仓资源存在性，与 15 篇 §7 Q5 口径一致；`40411` 由本篇按 13 §6.4 注「404xx 其余码由各篇分配」分配并登记 00 §6.4）。

### 7.3 误报回转与写操作（不新增路径）
- `SCRAP_MISREPORT` 走 12 篇审批中心，本篇不新增路径：发起 `POST /api/v1/approvals`（`type=SCRAP_MISREPORT`，`payload` 带报损单 id，权限 `scrap.misreport.request`；同一目标已有待审则返回那一条并 200/202），审批 `POST /api/v1/approvals/{id}/approve|reject`（`scrap.misreport.approve`，不能自批，12 §5.2）。通过后本篇同事务 `convert_hold(SCRAP_PENDING → RETURN_QC)` + 报损单 `VOIDED`。
- 报损单的提交 / 撤回 / 驳回 / 过账沿用本篇既有服务与状态机（§5），**13 篇的消费面只有 §7.1 / §7.2 两条读接口**，写动作都经审批中心或系统任务，不由后台直接调。

## 8. 并发与幂等
- 并发转超期：`uq_scr_srtn` + `uq_scr_source`，后到者撞唯一索引回滚；verify 两会话实测。
- 冻结重放：`uq_hold_op`（op_key `SRTO:{id}`）。

- 来源 `SUPPLIER_RETURN` 的报损单由 `trg_scr_srtn` 守卫：只能为 `AWAITING_PICKUP` 的退供单开单（`srtn_scrap_not_awaiting`）。退供单没有转 `OVERDUE_SCRAP` 并指回本单时，报损单只能取消或驳回，不能提交、审批或过账（`srtn_scrap_orphan`）。这一条兜住服务端条件更新 0 行却照样提交的情况（详见第 10 篇 §8）。

## 9. 异常与补偿
报损单驳回/取消：冻结由 `release_scrap_hold` 释放，退供单留在 `OVERDUE_SCRAP` 终态，人工经第 10 篇异常单处理。

## 10. 权限
- **读**：`inventory.expiry.view`（效期预警列表 / 详情）、`scrap.order.view`（报损单列表 / 详情）——两者都在 12 篇 §4.2 已登记（`scrap.order.view` 即 13 篇原写的 `scrap.view`），受仓数据权限约束（40311）。
- **写**：**点名**（12 篇 §4.2 已登记，长流复核 §10）——`scrap.order.create`（建单 / 提交，报损申请人）、`scrap.order.approve`（审批 / 过账 / 撤回，**SoD-4：审批人 ≠ 报损申请人**，12 篇 §4.2 规则表 `SoD-4`）、`inventory.expiry.scan`（效期扫描，系统任务身份）；超期转报损任务系统身份（`operator_id = 0`）。
- **冻结链接是单据的从属数据**：`GET /api/v1/scrap-orders/{id}` 的 `holds[]` 只返回**本单自己**的冻结行（`scrap_line.hold_id` 指向的 `stock_hold`），它是报损单的组成部分，凭 `scrap.order.view` 返回，**不需要** `inventory.hold.view`（02 §7.2 的冻结台账读接口才是独立权限点）；跨单查冻结用 02 的冻结台账接口。
- **误报回转**：发起 `scrap.misreport.request`（仓库主管）、审批 `scrap.misreport.approve`（1 人，不能自批）——口径见 12 篇 §5.2，接口见 §7.3。

## 11. 测试要点
`PICKUP_OVERDUE` 只能配 `SUPPLIER_RETURN`（正向 / 拒绝 / 变异）；`uq_scr_srtn` 在旧单取消后仍拦（`uq_scr_source` 放过）及变异；`trg_srtn_overdue` 的绕过矩阵、search_path 目录 + 劫持 + 变异，见第 10 篇 §11。

读接口契约（§7.1 / §7.2，服务端契约测试）：
- `days_before` 边界 `0` / `365` 通过、`-1` / `366` → 40001；`include_sell_expired=false` 排除 `sell_deadline < 今天` 的行、`true` 时 `sell_expired=true` 的行在内且在列表里标记；
- `sell_deadline IS NULL` 的批次不出现；`days_to_expiry` 允许为负且与 `sell_expired` 同号一致；
- **盘点期间可见性（长流复核 §7.1 的回归用例）**：把一条临期货所在库位置 `location.status='LOCKED'`（模拟 08 建盘点单），该行**仍必须出现在预警列表**里；变异：把数据源改回 `v_stock_available` → 该行消失（断言必须变红）。
- `zone_id` / `sku_id` 给跨仓值时返回空列表（不是 403）、不泄露；游标翻页不漏不重（按 `days_to_expiry, stock_id`）；
- 报损单列表 `status` / `source_type` 多值与白名单外值（→ 40001）、`created_from > created_to` → 40001、`created_at` 按仓时区日期过滤；
- 详情 `{id}` 同时接受数字 id 与 `SCR-` 单号；跨仓单号 → 404 `40411`（不是 403、不是空详情）；`record_only=true` 的详情 `holds[]` 为空。

## 13. 对抗评审攻击面
- 退供来源的孤儿报损单（退供单未转超期）能否被提交、审批或过账？

1. 能否用 `PICKUP_OVERDUE` 给别的来源报损、或给退供单开第二张报损单？
2. 能否不冻结就让退供单进入超期态（见 10 §13）？
3. 报损单换挂到别的退供单？
