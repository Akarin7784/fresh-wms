## 1. 业务范围与边界

服务对象是 **B2B 生鲜城配**：给商超、餐饮门店、社区团购履约点供货。单仓起步，模型按多仓设计。设计目标按优先级排：**账实一致 > 作业效率 > 可扩展到多仓**（原 §0.1）。

**系统内**：入库、上架、库存账、批次效期、补货移库、波次、拣货、复核装箱、发货、盘点、损耗、退货，以及分拣 H5/PDA 端、管理后台。

**系统外，只做集成**：采购合同、销售定价、财务结算、车辆调度、路径规划，分别由 ERP、TMS、财务系统负责。计费只记录作业量，账单由财务算；配送只下发运单、接收签收回传。

**一期范围（做到 M2，见 §12）**：主数据、库存核心、入库、出库与分配、波次与拣货、PDA 端、管理后台。司机端和商城端是**二期**，第 15 篇只写概要。

## 4. 工程分层

目录沿用原 §2.4。依赖方向用 import-linter 卡死，违反就让 CI 失败：

```
api  →  service  →  repository  →  db
  ↘        ↘            ↘
     domain（纯逻辑，不依赖任何层）
```

| 层 | 只做什么 | 禁止 |
|---|---|---|
| api | HTTP 翻译、参数解析（含 `Quantity` 解析）、权限依赖注入 | 写业务判断 |
| service | 编排、**事务边界**，单据状态和库存在同一事务里改 | 直接改 `status` 字段，直接写 `stock` 表 |
| domain | 状态机迁移表、FEFO、不变量、效期计算 | 依赖 ORM/框架 |
| repository | 查询、条件 UPDATE、插入 | 业务分支 |
| 库存原语 | 第 2 篇 §7.1 | 其他模块绕过原语写 `stock` |

## 5. 双库建模规则 R1–R12（修订版）

原 D3、R2、§3.3 之间互相矛盾：D3 和 R2 说"数量用 `NUMERIC(14,3)`"，§3.3 说"称重品绝不能用整数"，R2 后半句又说"SQLite 侧存整数厘"。附录 A 实测 SQLite 的 `NUMERIC(14,3)` 实际存成 REAL（`0.1+0.2+0.3 = 0.6000000000000001`），小赵在 PG 16.14 上复现了。**现统一如下，以本表为准**：

| 规则 | 内容 |
|---|---|
| R1 | 所有表用 `id BIGINT`，由应用层生成（雪花算法，§6.1），不用数据库自增 |
| **R2（修订）** | **数量**统一存 `BIGINT`，列名后缀 `*_qty_milli`，单位是 **SKU 基本单位（`sku.base_uom`）的千分之一**：KG 计的 SKU 就是克，PCS 计就是 0.001 个。**金额**统一 `BIGINT` 存"分"。两个库的 DDL 一致，**不再使用 `NUMERIC`**。接口层：出参固定返回 3 位小数字符串（`"12.500"`）；入参只收字符串，最多 3 位小数，**超过 3 位小数返回 400，不四舍五入**；作业单位换算成基本单位后如果不是整数 milli，也返回 400。全程不经过 `float`。库层用 `ck_*_int` 防止 SQLite 混进 REAL/TEXT |
| R3 | 时间戳存 UTC；**业务日期**（效期、作业日）按**仓库时区**（`warehouse.timezone`）计算和展示，不按浏览器或服务器时区 |
| R4 | 不用 JSONB、数组、ENUM；枚举用 `VARCHAR(32)` + `StrEnum` |
| R5 | 不用外键级联，只建索引 |
| R6 | 软删除用 `deleted_at` + 组合唯一 |
| R7 | 并发扣减只用条件 UPDATE + `rowcount` 判定，禁止 `SELECT FOR UPDATE`；多行按主键升序更新 |
| R8 | DDL 只走 Alembic batch 模式 |
| R9 | 布尔用 `SMALLINT` 0/1，列名 `is_xxx` |
| R10 | 全文检索隔离在 repository 的一个方法里 |
| R11 | 进入 UNIQUE 的列必须 NOT NULL + 哨兵值。**例外**：成组可空的业务键（如流水的 PDA 四列）必须加"全空或全非空"的 CHECK，并且用部分唯一索引（第 2 篇 `ck_mv_pda_src`） |
| R12 | 核心不变量要有应用层断言，库里再放一份 CHECK |

**单据表数量列的迁移**：第 2 篇已经把库存表和 `count_line` 改成 `*_qty_milli`。其余单据表（`inbound_line`、`outbound_line`、`pick_task_line`、`adjust_line`、`pack_box_line`）由各自模块的 PR 按本规则修改。`outbound_line` 由第 4 篇定义，见第 4 篇 §4。

## 6. 全局约定

### 6.1 ID：雪花算法

- 64 位：1 位符号 + 41 位毫秒时间戳（自定义纪元 `2026-01-01T00:00:00Z`）+ **10 位节点号** + 12 位序列。
- **节点号由中心在部署节点时分配**，写进节点配置文件（`WMS_NODE_ID`），中心维护分配登记表，不允许重复分配。启动时节点号缺失或越界就拒绝启动。**不依赖 Redis，也不依赖网络。**
- **时钟回拨**：检测到当前毫秒 < 上次发号毫秒时，**拒绝发号**，返回 `50302`，同时告警，不等待、不借位。NTP 只允许 slew，不允许 step（部署检查项）。
- **高水位（防重启后回拨，小吴 A2）**：发号器把"已预留到的毫秒时间戳"持久化在本地库（`id_node_hwm`，每个节点号一行），每 N ms（默认 N=2000）用条件更新预留一个窗口：`UPDATE id_node_hwm SET hwm_ms=:now+N WHERE node_id=:id AND hwm_ms=:old`。发号时间戳必须 < 已持久化的高水位，越过就先续窗口。启动时按差值处理（小吴 N1）：
  - `now ≥ hwm_ms`：直接启动。
  - `0 < hwm_ms − now ≤ N`：这是正常重启（崩溃自动拉起、滚动发布），因为高水位本来就往前预留了 N。**等到 `now ≥ hwm_ms` 再启动**，最多等 N 毫秒。
  - `hwm_ms − now > N`：判定为时钟真的回拨了，**拒绝启动并告警**，不自动跳过。
  - 测试用例：重启间隔 < N 能正常启动（等待时长 ≤ N）；把时钟往回调超过 N，拒绝启动。
- 进程内单例发号；同一节点上的多个 worker 进程必须分配**不同节点号**。
- ID 只保证唯一，**不保证跨节点单调**，任何业务逻辑都不能依赖 ID 的大小顺序（第 2 篇已经用 `ledger_seq` 做水位线）。

### 6.1a 单仓单写库（小吴 A1）

- **任何时刻，一个仓只有一个可写库**，称为该仓的权威库（authoritative DB）。登记在中心的 `warehouse_db_authority` 中，应用启动时校验"本节点是不是这个仓的权威库"，不是就只读。
- 切换权威库只能走**交接式故障切换**（handover failover）：旧库停写并导出最后水位 → 新库确认接收 → 中心改登记 → 新库开写。不允许两个库同时对同一个仓写入，也就不存在"离线双写后合并"。
- **一期建议（待 Yuri 定范围）**：**不做边缘节点**，只部署中心 PG；SQLite 只用于开发和测试。离线能力只在 PDA 端（离线队列 + 四元组幂等 + 待回库）。边缘节点相关规则（节点号、高水位、`synchronous`）先保留在设计里，二期再启用。

### 6.2 单号

- 格式：`{仓前缀}-{节点号}-{yyyyMMdd}-{序号}`，如 `SH01-0003-20261015-000842`。**节点号固定 4 位、左补零**（雪花节点号 10 位，取值 0–1023，4 位足够覆盖）。单据类型前缀（`OBT`、`PK` 等）放在仓前缀前面：`OBT-SH01-0003-20261015-000842`。
- 日期取**作业日**（`work_date`，按仓库时区计算）。
- 序号存在**本地数据库**的序列表（`numbering_segment`）里，每个 `(doc_type, warehouse, node, date)` 一行，用条件更新递增：
  ```sql
  UPDATE numbering_segment SET next_val = next_val + :n, version = version + 1
   WHERE seq_key = :k AND next_val = :expected   -- rowcount=0 就重读重试
  ```
  可以一次取一个号段（默认 50）放在内存里，进程重启时丢掉的号段只是浪费号，不会重号。**跨过作业日切换时刻时，必须丢弃内存里所有旧作业日的号段**（号段按 `(doc_type, warehouse, node, date)` 缓存，取号前先比对当前作业日，不一致就作废旧段、按新日期取段），避免切换后仍发出旧日期的单号（小吴 S2）。PG 和 SQLite 写法相同。
- 中心和各边缘节点的节点号不同，所以单号**天然不会撞号**，离线恢复后对账也不需要重新编号。所有 `code` 列保留 UK 兜底。

见 R2。值对象 `Quantity` 的规则见第 2 篇 §3.1，所有模块都复用这一个类。

### 6.4 错误码

**规则**：业务码是 **5 位纯数字，不加前缀**，**前 3 位就是 HTTP 状态码**，后 2 位是序号。`5xxxx` **只用于服务端错误**。业务码作为字符串返回，成功时为 `"0"`。码值集中定义在 `common/errors.py`，CI 检查有没有重复。

响应体沿用原 §6.1，只改 `code` 的格式：

```json
{ "code": "40920", "message": "任务已改派", "trace_id": "…", "data": null,
  "detail": { "task_id": 123, "confirmedLines": [ … ], "returnRecordId": 9001 } }
```

### 6.5 幂等

三层防线，下层兜住上层失效的情况：

1. **接口层**：所有 POST 必须带 `Idempotency-Key`（登录除外）。`idempotency_record` 跟业务写在**同一个库、同一个事务**里。同 key、同请求返回首次响应；同 key、不同请求体返回 **40910**，`detail.key_type = "IDEMPOTENCY_KEY"`。记录保留 24h。
   - **只缓存确定性结果**：2xx，以及明确的业务 4xx（400xx 参数类、409xx 冲突类）。**不缓存 422、5xx、429**：这些是现场可纠正或暂时性的错误（扫错库位、写锁超时、限流），同一个 key 重试时要重新执行。不缓存的响应不写 `idempotency_record`（随事务回滚）。
2. **业务层**：每类写操作都要有**业务唯一键**，`Idempotency-Key` 过期后靠它兜底。
   - 上游推单：`UNIQUE(source_system, source_order_no)`，重推返回 200 和已有单号。
   - **PDA 作业：四元组 `(task_id, line_no, device_instance_id, op_seq)`**。`device_instance_id` 在装机时生成并存在本地，重装或换机就换一个；`op_seq` 由 PDA 按任务行单调递增，重试时保持不变。同一四元组、同数量就回放之前的结果；同一四元组、不同数量返回 **40910**，`detail.key_type = "PDA_OP"`。`detail.key_type` 在 40910 里**总是存在**，前端据此区分提示。
   - **防超拣**：拣货确认在同一事务里依次做：四元组去重 → `UPDATE pick_task_line SET confirmed_qty_milli = confirmed_qty_milli + :qty WHERE id=:id AND confirmed_qty_milli + :qty <= planned_qty_milli` → 影响 0 行返回 **42214** → 写库存流水（第 2 篇 `consume`）。三步同事务，任一失败全部回滚。
   - 占用和冻结：`op_key` 唯一（第 2 篇）。
   - 待回库记录：按四元组唯一（第 4 篇 §7.3）。
3. **记账层**：流水唯一约束 `uq_mv_biz_line`、`uq_mv_pda_op`（第 2 篇 §4.4），撞约束就整个事务回滚，绝不二次扣减。

### 6.6 权限模型

沿用原 §6.4：RBAC + 数据权限（`user_warehouse`、`role_data_scope`）。权限点命名 `{模块}.{资源}.{动作}`，在代码里定义成枚举。三层校验：前端隐藏按钮**不是**安全边界，接口层的 `require_perm` 才是，数据层全局注入 `warehouse_id` 过滤。**不信任请求体里的 `warehouse_id`**。`X-Warehouse-Id` 必须同时满足：①在用户的仓库数据权限内；②跟路径或请求体里所指资源的所属仓一致（服务端按资源查出 `warehouse_id` 比对）。任一不满足返回 **403 `40311`**。系统管理员不能做业务操作。主管类操作（改派、resolve、越权分配、解冻、审批）全部写 `audit_log`，`audit_log` 只追加（第 12 篇）。

### 6.7 状态机写法

- 每种单据一张迁移表 `dict[str, set[str]]`，放在 `domain/state_machines.py`，全系统**只有** `transit()` 能改 `status`。
- 持久化时用条件更新：`UPDATE … SET status=:to, version=version+1 WHERE id=:id AND status=:from`。`rowcount=0` 说明状态已经被别人改了，返回 **40930**，并带上当前状态。
- 每篇模块文档的状态机都要给出：mermaid 状态图、迁移表、每条迁移的触发者、守卫条件、副作用（比如调用了哪个库存原语）。CI 穷举所有 `(from, to)` 组合做断言。
- 终态之后不允许再迁移；已发货的单只能走红冲。

### 6.8 时间

按 R3。作业日 `work_date` 由仓库的切换时刻计算（原 §3.3）。

## 7. 集成全景

沿用原 §7.1。入站（ERP、商城推单）落 `inbound_message` 做幂等；出站（入库完成、发货、库存快照）走 **outbox**：业务事务里写 `outbox_event`，投递任务异步推送，失败指数退避，超过次数进死信，死信可以人工重放，重放沿用原来的事件 id，由下游幂等。细节见第 11 篇。

```
ERP ──订单/采购单──▶ inbound_message ──▶ WMS ──outbox──▶ ERP / 商城 / 财务 / TMS
                                         ▲
                     PDA（离线队列 + 四元组幂等）
```
