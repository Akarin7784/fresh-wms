## 1. 业务范围与边界

服务对象是 **B2B 生鲜城配**：给商超、餐饮门店、社区团购履约点供货。单仓起步，模型按多仓设计。设计目标按优先级排：**账实一致 > 作业效率 > 可扩展到多仓**（原 §0.1）。

**系统内**：入库、上架、库存账、批次效期、补货移库、波次、拣货、复核装箱、发货、盘点、损耗、退货，以及分拣 H5/PDA 端、管理后台。

**系统外，只做集成**：采购合同、销售定价、财务结算、车辆调度、路径规划，分别由 ERP、TMS、财务系统负责。计费只记录作业量，账单由财务算；配送只下发运单、接收签收回传。

**一期范围（做到 M2，见 §12）**：主数据、库存核心、入库、出库与分配、波次与拣货、PDA 端、管理后台。所有模块（含司机端、商城端）先完成详细设计再开发：第 15 篇是司机端/商城端前端，第 16 篇是配送与签收后端。

目录沿用原 §2.4。依赖方向用 import-linter 卡死，违反就让 CI 失败：

```
api  →  service  →  repository  →  db
  ↘        ↘            ↘
     domain（纯逻辑，不依赖任何层）
```

| 层 | 只做什么 | 禁止 |

## 5. 双库建模规则 R1–R12（修订版）

原 D3、R2、§3.3 之间互相矛盾：D3 和 R2 说"数量用 `NUMERIC(14,3)`"，§3.3 说"称重品绝不能用整数"，R2 后半句又说"SQLite 侧存整数厘"。附录 A 实测 SQLite 的 `NUMERIC(14,3)` 实际存成 REAL（`0.1+0.2+0.3 = 0.6000000000000001`），小赵在 PG 16.14 上复现了。**现统一如下，以本表为准**：

| 规则 | 内容 |
|---|---|
| R1 | 所有表用 `id BIGINT`，由应用层生成（雪花算法，§6.1），不用数据库自增 |
| **R2（修订）** | **数量**统一存 `BIGINT`，列名后缀 `*_qty_milli`，单位是 **SKU 基本单位（`sku.base_uom`）的千分之一**：KG 计的 SKU 就是克，PCS 计就是 0.001 个。**金额**统一 `BIGINT` 存"分"。两个库的 DDL 一致，**不再使用 `NUMERIC`**。接口层：出参固定返回 3 位小数字符串（`"12.500"`）；入参只收字符串，最多 3 位小数，**超过 3 位小数返回 400，不四舍五入**；作业单位换算成基本单位后如果不是整数 milli，也返回 400。全程不经过 `float`。库层用 `ck_*_int` 防止 SQLite 混进 REAL/TEXT |
| R3 | 时间戳存 UTC；**业务日期**（效期、作业日）按**仓库时区**（`warehouse.timezone`）计算和展示，不按浏览器或服务器时区 |
| R4 | 不用 JSONB、数组、ENUM；枚举用 `VARCHAR(32)` + `StrEnum` |
| R5 | 不用外键级联，只建索引 |
| R6 | 软删除用 `deleted_at` + 组合唯一 |
| R7 | 并发扣减只用条件 UPDATE + `rowcount` 判定，禁止 `SELECT FOR UPDATE`；多行按主键升序更新 |
| R8 | DDL 只走 Alembic batch 模式 |
| R9 | 布尔用 `SMALLINT` 0/1，列名 `is_xxx` |
| R10 | 全文检索隔离在 repository 的一个方法里 |
| R11 | 进入 UNIQUE 的列必须 NOT NULL + 哨兵值。**例外**：成组可空的业务键（如流水的 PDA 四列）必须加"全空或全非空"的 CHECK，并且用部分唯一索引（第 2 篇 `ck_mv_pda_src`） |
| R12 | 核心不变量要有应用层断言，库里再放一份 CHECK |

**单据表数量列的迁移**：第 2 篇已经把库存表和 `count_line` 改成 `*_qty_milli`。其余单据表（`inbound_line`、`outbound_line`、`pick_task_line`、`adjust_line`、`pack_box_line`）由各自模块的 PR 按本规则修改。`outbound_line` 由第 4 篇定义，见第 4 篇 §4。

## 6. 全局约定

### 6.1 ID：雪花算法

- 64 位：1 位符号 + 41 位毫秒时间戳（自定义纪元 `2026-01-01T00:00:00Z`）+ **10 位节点号** + 12 位序列。
- **节点号由中心在部署节点时分配**，写进节点配置文件（`WMS_NODE_ID`），中心维护分配登记表，不允许重复分配。启动时节点号缺失或越界就拒绝启动。**不依赖 Redis，也不依赖网络。**
- **时钟回拨**：检测到当前毫秒 < 上次发号毫秒时，**拒绝发号**，返回 `50302`，同时告警，不等待、不借位。NTP 只允许 slew，不允许 step（部署检查项）。
- **高水位（防重启后回拨，小吴 A2）**：发号器把"已预留到的毫秒时间戳"持久化在本地库（`id_node_hwm`，每个节点号一行），每 N ms（默认 N=2000）用条件更新预留一个窗口：`UPDATE id_node_hwm SET hwm_ms=:now+N WHERE node_id=:id AND hwm_ms=:old`。发号时间戳必须 < 已持久化的高水位，越过就先续窗口。启动时按差值处理（小吴 N1）：
  - `now ≥ hwm_ms`：直接启动。
  - `0 < hwm_ms − now ≤ N`：这是正常重启（崩溃自动拉起、滚动发布），因为高水位本来就往前预留了 N。**等到 `now ≥ hwm_ms` 再启动**，最多等 N 毫秒。
  - `hwm_ms − now > N`：判定为时钟真的回拨了，**拒绝启动并告警**，不自动跳过。
  - 测试用例：重启间隔 < N 能正常启动（等待时长 ≤ N）；把时钟往回调超过 N，拒绝启动。
- 进程内单例发号；同一节点上的多个 worker 进程必须分配**不同节点号**。
- ID 只保证唯一，**不保证跨节点单调**，任何业务逻辑都不能依赖 ID 的大小顺序（第 2 篇已经用 `ledger_seq` 做水位线）。

### 6.1a 单仓单写库（小吴 A1）

- **任何时刻，一个仓只有一个可写库**，称为该仓的权威库（authoritative DB）。登记在中心的 `warehouse_db_authority` 中，应用启动时校验"本节点是不是这个仓的权威库"，不是就只读。
- 切换权威库只能走**交接式故障切换**（handover failover）：旧库停写并导出最后水位 → 新库确认接收 → 中心改登记 → 新库开写。不允许两个库同时对同一个仓写入，也就不存在"离线双写后合并"。
- 中心 PG 和仓库边缘节点（SQLite）都是正式部署形态，单写库约束在两种形态下怎么落地、断网和恢复联网怎么处理，见 **§9.1 部署形态**。

### 6.2 单号

- 格式：`{仓前缀}-{节点号}-{yyyyMMdd}-{序号}`，如 `WHSH01-0003-20261015-000842`。**节点号固定 4 位、左补零**（雪花节点号 10 位，取值 0–1023，4 位足够覆盖）。单据类型前缀放在仓前缀前面：`OBT-SH01-0003-20261015-000842`。
  **已登记的单据类型前缀**（新增前缀先登记到本篇，`doc_type` 与之一一对应）：`OBT`（出库单）、`PK`（波次 / 拣货任务）、`INB`（入库单）、`CNT`（盘点单，08）、`ADJ`（调整单，08；02 §4.4.2 示例已用）、`BOX`（箱码，06）、`SHP`（发运单，06，06 §12 Q6 待确认，本篇按其建议登记）、`RPL`（补货任务，07）、`RPD`（补货需求，07）、`MV`（移库单，07）。`RSV`（退货预约）、`SCR`（报损单）、`IQF`（入库质量反馈）等沿用各自篇的定义。
- 日期取**作业日**（`work_date`，按仓库时区计算）。
- 序号存在**本地数据库**的序列表（`numbering_segment`）里，每个 `(doc_type, warehouse, node, date)` 一行，用条件更新递增：
  ```sql
  UPDATE numbering_segment SET next_val = next_val + :n, version = version + 1
   WHERE seq_key = :k AND next_val = :expected   -- rowcount=0 就重读重试
  ```
  可以一次取一个号段（默认 50）放在内存里，进程重启时丢掉的号段只是浪费号，不会重号。**跨过作业日切换时刻时，必须丢弃内存里所有旧作业日的号段**（号段按 `(doc_type, warehouse, node, date)` 缓存，取号前先比对当前作业日，不一致就作废旧段、按新日期取段），避免切换后仍发出旧日期的单号（小吴 S2）。PG 和 SQLite 写法相同。
- 中心和各边缘节点的节点号不同，所以单号**天然不会撞号**，离线恢复后对账也不需要重新编号。所有 `code` 列保留 UK 兜底。

### 6.4 错误码

**规则**：业务码是 **5 位纯数字，不加前缀**，**前 3 位就是 HTTP 状态码**，后 2 位是序号。`5xxxx` **只用于服务端错误**。业务码作为字符串返回，成功时为 `"0"`。码值集中定义在 `common/errors.py`，CI 检查有没有重复。

响应体沿用原 §6.1，只改 `code` 的格式：

```json
{ "code": "40920", "message": "任务已改派", "trace_id": "…", "data": null,
  "detail": { "task_id": 123, "confirmedLines": [ … ], "returnRecordId": 9001 } }
```

### 6.5 幂等

三层防线，下层兜住上层失效的情况：

1. **接口层**：所有 POST 必须带 `Idempotency-Key`（登录除外）。`idempotency_record` 跟业务写在**同一个库、同一个事务**里。同 key、同请求返回首次响应；同 key、不同请求体返回 **40910**，`detail.key_type = "IDEMPOTENCY_KEY"`。记录保留 24h。
   - **只缓存确定性结果**：2xx，以及明确的业务 4xx（400xx 参数类、409xx 冲突类）。**不缓存 422、5xx、429**：这些是现场可纠正或暂时性的错误（扫错库位、写锁超时、限流），同一个 key 重试时要重新执行。不缓存的响应不写 `idempotency_record`（随事务回滚）。
2. **业务层**：每类写操作都要有**业务唯一键**，`Idempotency-Key` 过期后靠它兜底。
   - 上游推单：`UNIQUE(source_system, source_order_no)` + `source_hash`。同号同内容重推返回 200 和已有单号；同号不同内容返回 40910，`key_type=SOURCE_ORDER`（第 4 篇 §7.1）。
   - **PDA 作业：四元组 `(task_id, line_no, device_instance_id, op_seq)`**。`device_instance_id` 在装机时生成并存在本地，重装或换机就换一个；`op_seq` 由 PDA 按任务行单调递增，重试时保持不变。同一四元组、同数量就回放之前的结果；同一四元组、不同数量返回 **40910**，`detail.key_type = "PDA_OP"`。
   - **司机端作业（第 16 篇）：`(waybill_no, stop_no, device_instance_id, op_seq)`**，规则跟 PDA 四元组相同；同键不同内容返回 **40910**，`detail.key_type = "POD_OP"`。站点已有有效签收返回 40950。
   - **司机端签收更正**：必须带被更正签收的 `corrected_pod_id`。同一更正键 `(driver_id, correction_client_id)`（长期去重）不同内容返回 40910，`detail.key_type = "POD_CORRECT"`。容差内的更正直接生效（不建审批单，同事务执行，第 16 篇 §6.3a）；超出容差才需主管审批。
   - `detail.key_type` 在 40910 里**总是存在**（`IDEMPOTENCY_KEY` / `PDA_OP` / `POD_OP` / `POD_CORRECT` / `SOURCE_ORDER` / `LIVE_WEIGH` / `LIVE_INSPECT` / `LIVE_DEATH` / `LIVE_SHRINK` / `PROCESS_REPORT` / `PROCESS_ISSUE` / `PROCESS_REVERSAL` / `OFFLINE_PAPER` / `INBOUND_MESSAGE` / `APPROVAL_REQUEST` / `USER_DEVICE_BINDING` / `OFFLINE_TOKEN` / `SYS_USER` / `DEVICE_RECONNECT` / `SYS_ROLE` / `SYS_PERMISSION` / `SYS_USER_ROLE` / `SYS_ROLE_PERM` / `SYS_USER_WAREHOUSE` / `API_CREDENTIAL`（后十一个：第 12 篇表的同键重复写入，见 §6.4 第 12 篇库层名表）），前端据此区分提示。
   - **防超拣**：拣货确认在同一事务里依次做：四元组去重 → `UPDATE pick_task_line SET confirmed_qty_milli = confirmed_qty_milli + :qty WHERE id=:id AND confirmed_qty_milli + :qty <= planned_qty_milli` → 影响 0 行返回 **42214** → 写库存流水（第 2 篇 `consume`）。三步同事务，任一失败全部回滚。
   - 占用和冻结：`op_key` 唯一（第 2 篇）。
   - 待回库记录：按四元组唯一（第 4 篇 §7.3）。
3. **记账层**：流水唯一约束 `uq_mvk_biz_line`、`uq_mvk_pda_op`（建在 `stock_movement_key` 上，第 2 篇 §4.4），撞约束就整个事务回滚，绝不二次扣减。

### 6.6 权限模型

沿用原 §6.4：RBAC + 数据权限（`user_warehouse`、`role_data_scope`）。权限点命名 `{模块}.{资源}.{动作}`，在代码里定义成枚举。三层校验：前端隐藏按钮**不是**安全边界，接口层的 `require_perm` 才是，数据层全局注入 `warehouse_id` 过滤。**不信任请求体里的 `warehouse_id`**。`X-Warehouse-Id` 必须同时满足：①在用户的仓库数据权限内；②跟路径或请求体里所指资源的所属仓一致（服务端按资源查出 `warehouse_id` 比对）。任一不满足返回 **403 `40311`**。系统管理员不能做业务操作。主管类操作（改派、resolve、越权分配、解冻、审批）全部写 `audit_log`，`audit_log` 只追加（第 12 篇）。

`GET /api/v1/me` 和终端心跳响应都带以下字段，前端据此置灰操作和显示倒计时，不写死清单：

### 6.7 状态机写法

- 每种单据一张迁移表 `dict[str, set[str]]`，放在 `domain/state_machines.py`，全系统**只有** `transit()` 能改 `status`。
- 持久化时用条件更新：`UPDATE … SET status=:to, version=version+1 WHERE id=:id AND status=:from`。`rowcount=0` 说明状态已经被别人改了，返回 **40930**，并带上当前状态。
- 每篇模块文档的状态机都要给出：mermaid 状态图、迁移表、每条迁移的触发者、守卫条件、副作用（比如调用了哪个库存原语）。CI 穷举所有 `(from, to)` 组合做断言。
- 终态之后不允许再迁移；已发货的单只能走红冲。

### 6.8 时间

按 R3。作业日 `work_date` 由仓库的切换时刻计算（原 §3.3）。

**时间约定（#2 第九轮，硬规则）**：

1. **一律 UTC、整秒**。所有落库时间列语义都是 UTC，精度到秒。**客户端提交的时间也必须是整秒 `YYYY-MM-DD HH:MM:SS`（UTC）**：带 `T`、带时区后缀（`Z` / `+08:00`）或带小数秒一律拒 **400 `40003 CLIENT_TIME_INVALID`**（第 5 篇旧稿的 `2026-10-15T02:13:41Z` 是反例）。PG 侧由第 3 / 7 条的服务端改写与库层守卫兜底，SQLite 侧由第 4 条的格式 CHECK 兜底。
2. **列型只用 `TIMESTAMP`（不带时区），禁止 `timestamptz` / `TIMESTAMP WITH TIME ZONE`**。带时区类型会按会话时区换算，SQLite 没有对应类型，两库会不一致。`verify.sh` 断言 public 下 timestamptz 列数为 0，并在会话 `TIME ZONE 'Asia/Shanghai'` 下经第 2 篇路径写入，断言落库值是 UTC。
3. **服务端产生的时间由库写**（审批、状态、审计、建单时间等）。PG：`date_trunc('second', now() AT TIME ZONE 'UTC')`；默认值写 `DEFAULT (date_trunc('second', now() AT TIME ZONE 'UTC'))`，不能让调用方改的列再用 BEFORE 触发器强制覆盖（表属主迁移脚本可豁免，须在本篇登记）。
4. **SQLite**：时间列只收整秒 `YYYY-MM-DD HH:MM:SS`（`GLOB` + `strftime('%s', x) IS NOT NULL`，拒小数秒、`T`、时区后缀、非法日期）；由服务端写的时间只接受与 `now` 相差 ±300 s 以内；日期列只收 `YYYY-MM-DD` 且 `date(x) IS x`。
5. **比较按整数秒**：SQLite 一律 `CAST(strftime('%s', x) AS INTEGER)` 比较，禁止按文本比较；PG 直接比较 TIMESTAMP。
6. **过期 / 截止类时间由库计算或限上界**，调用方不能写成"永不过期"（包括写成 NULL）。例：第 2 篇 `stock_reservation.expires_at` 不传时由库算成 `created_at + 24h`；**允许缩短**（更早过期 = 更早释放预占，更安全），**不许超过 `created_at + 24h`**（`ck_res_ttl`），**不许为 NULL**（PG 列 `NOT NULL`；SQLite `trg_res_expires_lock` → `reservation_expires_null`）。`created_at` 写入后不可改（`reservation_created_at_immutable`）。
7. **事件时间由服务端强制**：`occurred_at`、`received_at`、`reported_at` 这类事件发生时间一律由库 / 服务端按第 3 条写入，不收客户端值。**只有确实存在设备产生的时间**（离线补传、PDA 本地时钟）的表才加可选列 `client_occurred_at`（`TIMESTAMP`，UTC 整秒，同样受第 4 条格式约束），**只用于展示和排障**，不参与任何业务判断、窗口计算、排序、对账或清理（purge）条件；没有设备时间来源的表不加此列。第 2 篇 `stock_movement.occurred_at` / `stock_movement_key.occurred_at` 是库强制的过账时间，**不设** `client_occurred_at`（设备时间在作业单据上，不进流水）：PG 用分区父表上的 BEFORE INSERT 触发器 `trg_mv_zclock` / `trg_mvk_zclock`（自动克隆到各月分区）改写成 `date_trunc('second', now() AT TIME ZONE 'UTC')`；客户端值与库时钟不在同一月（会落到别的分区，BEFORE 行触发器不能换分区）时拒 `movement_clock_skew` → **40003**；表属主（迁移 / 期初导入）豁免，同第 3 条。PG 上**显式传 `occurred_at = NULL`** 不会被改写：NULL 先按分区键路由到 default 分区，再按月份判定，得到 `movement_clock_skew`（40003）；02 原语不传这一列（走 DEFAULT），不受影响，调用方也不要显式传 NULL。SQLite 不能改 `NEW`，`trg_mv_clock` / `trg_mvk_clock` 拒非整秒 UTC、小时 > 23（`24:00:00` 能被 `strftime` 解析，第十二轮补 `substr(x,12,2) <= '23'`）或与 `now` 相差 > 300 s（`movement_clock_skew` → 40003）；`trg_res_clock` / `ck_res_ttl` 同样补了小时检查。
8. **落地情况**：第 2 篇已落地：`stock`、`stock_reservation`（默认值 + 触发器）、`stock_movement` / `stock_movement_key`（第十一轮，见第 7 条）；第 1 篇已落地：`warehouse` / `zone` / `location` / `sku` / `lot` 共 10 个 `created_at` / `updated_at` 改成 `DEFAULT (date_trunc('second', now() AT TIME ZONE 'UTC'))`（verify 两库各有"10/10 + 变异"断言，见第 1 篇 §4.8；本篇主数据没有客户端提交的时间列，因此不引入第 4 条的 ±300 s 窗口）；第 10 篇 `supplier_return`（`trg_srtn_zclock`）、第 11 篇 outbox 已按本节写。其余各篇（03、04、05、06、08、09、11 其余表、12、17、18）的 `DEFAULT now()` 仍是裸 `now()`（会话时区 + 微秒），由各篇 owner 按本节改，进度记在 #14。
9. **入库日期 `lot.receive_date` 只存日期**（第十一轮）：PG 列型 `DATE`；SQLite `ck_lot_recv_ts` 只收 `YYYY-MM-DD` 且 `date(x) IS x`，拒带时间（含 `00:00:00`）、`24:00:00`、时区偏移 / `Z`、斜杠、紧凑写法 `20261015`、非补零写法。需要入库时刻的用入库单上的事件时间，不用 `receive_date`。

### 6.9 PG 函数 search_path（硬规则）

所有 PL/pgSQL 函数（触发器函数、`SECURITY DEFINER` 函数、库存原语）**必须**固定 `SET search_path = pg_catalog, public, pg_temp`：**`pg_temp` 必须显式写出，且放在最后**。

原因：search_path 里没写 `pg_temp` 时，PG 会把会话临时 schema 隐式放在**最前面**查表。`wms_app` 默认有库级 `TEMP` 权限，可以建同名临时表盖住 public 的真表，绕过触发器守卫（小玛丽 srtn-final2 实测）。`pg_catalog, public` 不够。

`verify.sh` 2z 节：目录断言（public 下所有固定 search_path 的函数都必须正好是这一串）+ `wms_app` 建同名临时表劫持第 2、9、11、12 篇函数 + 去掉 `pg_temp` 的变异必须变红。SQLite 没有对应攻击面（没有 schema 搜索路径，触发器体里的表名绑定到 main），不加对应用例。

### 6.10 SQLite 防 REPLACE（硬规则，#2 第十一轮；第十二轮逐唯一键、扩到全部表；第十三轮删实打缺口名单）

SQLite 的 `INSERT OR REPLACE` / `REPLACE INTO` 遇到主键或**任一**唯一键冲突时**先删旧行再插新行**，而且（`recursive_triggers` 默认关）**不触发 DELETE 触发器**，隐式删除也不能指望外键兜底（只有被引用的父行才会报 FOREIGN KEY）。所以只靠 `BEFORE UPDATE` / `BEFORE DELETE` 拦截的表可以被 REPLACE 整行改写；去重 / 序号类唯一键（幂等键、账序、条码、快照日）会被 REPLACE 静默"抢走"（小玛丽 r11 X1：`stock_movement_key` 换 `movement_id`、撞 `idempotency_key` 或 `(stock_id, stock_seq)` 就删掉旧 key 行，留下孤儿流水）。

1. 表 DDL **禁止** `ON CONFLICT REPLACE`（注释里出现也判红，偏保守，接受）。
2. **每张有唯一键的表**，**每个**唯一键（主键、UNIQUE 约束、唯一索引；部分唯一索引按同一谓词收窄）都要被 no-REPLACE 触发器覆盖：`BEFORE INSERT ON T`，`WHEN EXISTS (SELECT 1 FROM T x WHERE … x.col = NEW.col …)`，`RAISE(ABORT, …)`。可以一个键一个触发器，报错尾部写成与 UNIQUE 冲突同形（`…: T.col1, T.col2`），两库用例按同一个键断言。超集键由子集键覆盖。表达式唯一索引一律红（改成列索引或逐键登记）。
3. 静态检测（`verify_sqlite.py` 2z3 节）：守卫 = `BEFORE INSERT ON T` + `RAISE(ABORT` + `EXISTS (SELECT 1 FROM T`；键被覆盖 = 某个守卫里该键**每一列**都出现 `x.col = NEW.col`。只写 `WHEN s='never'`、只写 `NEW.k IS NULL` 或少一列的守卫都不算。
4. 实打检测（2z3b 节）：verify 跑完后，对每张表的每个唯一键（部分索引按谓词取样本行，命中判定也带谓词）造一条只撞这个键的冲突行，先在"去掉全部触发器"的保存点里证明这条 REPLACE 会删掉原行（打到了键），再在只留守卫的库上执行，必须被拒且原行每一列都还在；随后去掉守卫的变异必须通过且原行被删。**造不出样本 = 红；去触发器后 REPLACE 执行了却没删到原行 = 造样本失败，红，绝不当通过**。第十三轮删掉了"实打缺口"名单（小玛丽 r12 B1：12 个键都能造；名单会把被削弱的守卫一起放过），改为补无子行种子（`return_reservation`、`user_device_binding`、`live_tank_hold`、`live_shrink_settlement`、`live_inspection`、`process_issue`、`process_report`、`zone` 各一条）；`live_tank_hold(id)`、`process_issue(id)` 用手写实打（同主键、其余唯一键落在同一行，同样两段判定）。变异：`trg_lw_dup` 业务键分支加 `AND NEW.result='NEVER'`（静态仍绿）→ 实打必须红。
5. **名单全部冻结基线、只能缩小**（基线外 → 红；已修好还在名单 → 红）：
   - 表级豁免（受锁但还没有守卫，第十一轮 7 张，第十二轮删掉 01 `lot`、02 `stock_ledger_line`，第 11 篇时间增量补 `trg_upl_no_replace` 后删掉 11 `upstream_push_log`，现 4 张）：03 `inbound_order`；10 `supplier_return`；17 `process_bom`、`process_bom_line`。
   - 键级豁免（表有守卫但这几个键还没拦）：10 `exception_case.code`；17 `process_order.uq_prc_apr`；09 `scrap_line (scrap_id, line_no)`、`scrap_order` 的 `uq_scr_srtn` / `uq_scr_source` / `code`；02 `stock_recon_alert.uq_recon_open`（第十三轮由表级收窄而来）。
   - `REPLACE_OK`（REPLACE 可接受）：只剩 01 `sku_unit`（没有任何表引用它，按 `(sku_id, uom)` 换 id REPLACE 等价于改写换算系数，与 UPDATE 能做的一样）。第十三轮移出：`warehouse` / `zone` / `location` / `sku`（小玛丽 r12 B2：子表的 `sku_id` / `location_id` / `zone_id` / `warehouse_id` 大多没声明外键，按业务键换 id REPLACE 会静默删父行留孤儿；"外键兜底"只在恰好有已声明外键的子行时成立）→ 全部唯一键加守卫；`stock_recon_alert` → 加 RESOLVED 终态锁 + `id` 守卫，收窄为键级豁免 `uq_recon_open`（未闭环 UPSERT 需要）。

6. 第 1/2 篇（第十二 / 十三轮）已全部覆盖：`warehouse`、`zone`、`location`、`sku`、`lot`、`sku_barcode`、`stock`、`stock_reservation`、`stock_hold`（含 `uq_hold_return`）、`stock_hold_release`、`stock_ledger_line`、`stock_movement`、`stock_movement_key`（5 个唯一键各一个触发器）、`stock_snapshot_daily`。第 11 篇（时间增量）已全部覆盖：`outbox_event`（PK、`uq_outbox_seq` 按 `seq > 0`、`uq_outbox_dead_bizkey` 按 `status = 'DEAD'`）、`idempotency_record`、`upstream_push_log`、`offline_paper_record`（PK、`uq_paper_bizkey`）、`inbound_message`（PK、`uq_in_msg`）、`numbering_segment`（PK）；`inbound_message`（判重键不可改）与 `numbering_segment`（只许前进）现为受锁表。

## 7. 集成全景

沿用原 §7.1。入站（ERP、商城推单）落 `inbound_message` 做幂等；出站（入库完成、发货、库存快照）走 **outbox**：业务事务里写 `outbox_event`，投递任务异步推送，失败指数退避，超过次数进死信，死信可以人工重放，重放沿用原来的事件 id，由下游幂等。细节见第 11 篇。

应用登录角色继承 `NOLOGIN` 的 `wms_app`，连接上的 `current_user` 不是 `wms_app`。`outbox_event` 的插入不按角色名判断，按是不是这张表的属主判断（第 2 篇 `trg_outbox_insert_pending`）。不是表属主的角色插入时，`status` 必须是 `PENDING` 且 `sent_at` 为空，否则直接拒绝，错误是 `outbox_insert_not_pending`。非法状态不改写成 `PENDING`。表属主是建表的迁移角色，种子和迁移可以插入其他状态。SQLite 没有角色，同一条触发器对所有插入生效，`FAILED` 同样拒绝。

```
ERP ──订单/采购单──▶ inbound_message ──▶ WMS ──outbox──▶ ERP / 商城 / 财务 / TMS
                                         ▲
                     PDA（离线队列 + 四元组幂等）
```

## 9. 部署

### 9.1 部署形态

**中心 PG** 和**仓库边缘节点（SQLite）**都是正式部署形态，按同一套规则设计，不按期次切分。各模块文档的"离线差异"一律引用本节，只写本模块特有的部分。

| 形态 | 部署位置 | 该仓的权威库 | 仓内终端连接 | 适用 |
|---|---|---|---|---|
| A 中心直连 | 中心机房 / 云 | 中心 PG | 经公网/专线直连中心 | 网络稳定的仓 |
| B 边缘节点 | 仓内服务器 | 仓内 SQLite（WAL + `synchronous=FULL`） | 仓内局域网连边缘节点 | 网络不稳、要求断网可作业的仓 |

**① 每仓单写库**（§6.1a）
- 每个仓在中心 `warehouse_db_authority` 里登记唯一的权威库。形态 B 下，该仓的作业数据（库存、单据、任务、流水）**只在边缘节点写**；中心保存的是这个仓的**只读镜像**，用于汇总报表、跨仓查询和对接 ERP，中心对这个仓的作业表不开写路径。
- 主数据（SKU、库位、用户权限等）**以中心为准**，边缘节点只持有只读副本，按版本号下发。
- 形态 A、B 之间切换，或者更换边缘硬件，只能走交接式故障切换（§6.1a）。

**② 断网运行（形态 B）**
- 仓内作业照常：收货、分配、波次、拣货、复核、发货都在边缘节点完成，ID 和单号用本节点的节点号在本地生成（§6.1、§6.2），不依赖中心。
- 发往中心或外部的消息（入库完成、发货、库存快照、签收）写本地 `outbox_event`，按节点内单调递增的 `seq` 排队，联网后投递。
- 上游（ERP、商城）发来的新单、取消先落中心 `inbound_message`，在中心排队，联网后下发到边缘节点。
- 断网期间主数据不更新，边缘节点按最后一个版本运行。引用了边缘侧尚未收到的主数据的单据进入"待主数据"状态，不丢弃。

**③ 恢复联网后的数据回传与冲突规则**
- **边缘 → 中心**：按 `(node_id, seq)` 严格顺序回传，中心按事件 id 幂等应用到镜像表。发现序号缺口就暂停该节点的应用并请求补发，不跳号。
- **中心 → 边缘**：新单、取消、主数据按中心侧 `seq` 顺序下发，边缘按 `inbound_message` 幂等应用。
- **冲突规则**：每仓只有一个写库，**不存在行级数据合并**，只有"命令跟当前状态不符"的业务冲突，一律按**权威库的当前状态**裁决，裁决结果作为事件回传：
  - 取消命令到达时订单已拣或已发：按第 4 篇状态机处理（已拣转拣货后取消，需主管；已发拒绝，回传 40930 结果事件，上游走红冲）。
  - 上游同单号不同内容：40910 `SOURCE_ORDER`。
  - 主数据：版本号高的生效，低版本或重复版本忽略；正被未完结单据引用的库位、SKU 的停用命令，延迟到单据完结后生效。
  - PDA、司机端的离线补传冲突按各自业务键处理（第 4、5、14、16 篇），与边缘 ↔ 中心回传无关。
- 回传积压超过阈值（默认 1 小时或 10 万条）告警；中心报表对该仓标注"数据截至 {最后应用时间}"。

**④ 节点号分配**
- 中心维护 `node_registry(node_id UK, warehouse_id, form A/B, role, status, assigned_at)`。节点号 0–1023 在中心节点和所有边缘节点之间**全局唯一**，部署时由中心分配并写进节点配置。
- 更换硬件或重装的节点**分配新号**，旧号标记退役，**永不复用**。
- 同一节点上每个 worker 进程各占一个节点号（§6.1）。

**写节点切换（补充）**
- 幂等记录、PDA/司机端业务键唯一约束、待回库记录都在该仓权威库里，随库迁移，新写节点直接继承，不重建、不清空；切换完成前旧节点只读。
- `GET /api/v1/warehouses/{warehouse_code}/write-endpoint` 返回 `{endpoint, epoch}`，**中心和边缘节点本地都提供**（边缘节点返回它自己持有的值）。客户端缓存上次取到的地址和 epoch；取不到时用缓存继续作业，断网不影响作业。收到 50301 或 `epoch` 变化时重新获取（50304 不触发重新获取），再按原幂等键和序号依次重提交。
- **防脑裂（epoch 栅栏）**：epoch 存在权威库的 `write_epoch` 表里，每次切换加 1。写请求必须带 `X-Write-Epoch`；节点发现请求的 epoch 小于本库 epoch，或者自己已经被标记为被取代（库里存在更大的 epoch），就拒绝写入并返回 50303 STALE_WRITE_NODE。新节点必须在旧节点已确认只读之后，或者走下面的非计划切换流程，才能拿到新 epoch。
- **非计划切换（边缘硬件故障）**：
  - **备份**：SQLite WAL 持续增量备份到中心（以及仓内第二块盘），**RPO ≤ 60 秒**，每天做一次全量备份。
  - **切换**：由一人发起，再由仓库主管和中心运维两人确认（共三人，发起人不能兼任确认人，按第 12 篇 SoD 与 `approval_request`），强制把旧节点标为被取代（epoch 加 1，旧节点上线后只读），从最近的备份恢复到备用机。发起 / 确认接口与权限点（`system.failover.confirm`）登记在第 11 篇 §7，审批类型见 §6.6.1 `UNPLANNED_FAILOVER`。
  - **发号**：非计划切换一律按「更换节点」处理（规则④）：新节点**分配新节点号，旧号退役**，不在旧号上抬高水位；单号里带节点号，所以 ID 和单号都不会与丢失窗口内已发出的值冲突。验收用例：从 60 秒前的备份恢复后，新发的 ID 和单号与中心镜像无冲突。
  - **单据核对**：管理后台操作和上游推单没有终端 outbox。恢复时用中心镜像（含边缘节点已回传的流水和事件）和集成层的上游入站推送日志（第 11 篇），逐单核对丢失窗口内的单据；镜像或推送日志里有、恢复后的库里没有的，进异常队列 `FAILOVER_GAP`，由主管补录或要求上游重推（同来源单号，按 40910/幂等规则判重）。
终端 outbox 按原业务键重提交，补上 RPO 窗口内丢失的写入，幂等保证不会重复入账。
  - **镜像重建（N2）**：单据核对（上一条）完成后，中心把该仓镜像中**备份点之后**回传的事件标记作废（归档保留，不删），再以恢复后的权威库为准**全量重建**该仓镜像（库存快照 + 事件水位），之后的事件按新节点号正常回传。顺序固定为：先用旧镜像核对单据，后作废并重建，防止终端重提交按新事件 id 二次入镜像。验收用例：恢复并补数后，镜像库存与权威库逐行一致。
  - **对账**：恢复后到开放作业之前，必须对故障前 RPO 窗口内有变动的库位做一次动碰盘点（第 8 篇），差异按盘点流程调整，对账完成才开放作业。
- **断网期间可售量与 `stale_stock_policy`**：中心镜像落后超过阈值（默认 5 分钟）时，该仓可售量标记为不可信，处理策略由配置项 `stale_stock_policy` 决定（`PAUSE` / `DEGRADE`；DEGRADE 按镜像值乘以系数 r 降额接单）。**默认 `PAUSE`（Yuri 已定）**，暂停范围：
  - **暂停**：凡是跨网点占用或移动库存的操作——新分配 / 预占（商城、上游新单对该仓的占用）、调拨（跨仓移库）、波次释放、活鲜出池称重扣库存。返回 503 `50304` STALE_STOCK_PAUSED，对应 `paused_actions` 的 `ALLOCATE` / `TRANSFER` / `WAVE_RELEASE` / `LIVE_WEIGH_OUT`；调用方停止该操作、不自动重试，等 `/me`/心跳 `paused` 解除后再提交，不丢单。
  - **离线继续**：已下发拣货任务的执行（拣货确认、复核、发货按已分配量走）、收货登记、签收。这些操作在本仓权威库内完成，按原业务键入 outbox，恢复后回传。
  - **最长离线 12 小时**：超过后离线继续的操作也停止受理新的（已在途的补传仍接收），需中心运维确认后才恢复；与第 12 篇离线令牌最长 12 小时一致。
  - **重连后对账**：先回放 outbox、核对镜像与权威库逐行一致（同 N2 的顺序），再解除 PAUSE；对账冲突（同一库存被两边占用、单据状态不一致等）不自动合并，进异常队列（`stock_recon_alert` / 待回库同类队列）由人工处理，处理完才恢复该仓的新分配。
