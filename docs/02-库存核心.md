## 1. 职责与边界

### 1.1 本模块负责

1. **库存余额**：`stock` 一行代表一个记账维度 `仓库 + 库位 + SKU + 批次 + 容器`（原文档 §4.1，I6）上的五个数量：在库量 `on_hand`，以及四个占用列 `allocated / reserved / quality_hold / hold_qty`。
2. **占用明细**：`stock_reservation`（预占、分配）和 `stock_hold`（质检冻结、人工冻结）。四个占用列是这两张表的**物化汇总**（I3）。
3. **库存原语**（§7.1）：入账、出账、移库、预占、预占转分配、释放、消耗、冻结、解冻。所有改库存的业务都**只能**调这些原语，不许直接写 `stock`。
4. **库存流水** `stock_movement`：只追加，每一次 `on_hand` 变化对应一条流水，与余额在同一事务。
5. **不变量**：库层 CHECK + 应用层断言两道防线（§4.3）。
6. **快照与对账**：日终快照、流水回放对账、占用汇总对账。**只告警，不自动修数**（§6.4）。
7. **FEFO 钩子**：给第 4 篇提供"候选库存切片"查询和"按分配结果原子占用"两个接口。排序与分配算法本身归第 4 篇（§7.3）。
8. **前提**：每仓只有一个权威写库（00 §6.1a；一期中心 PG，SQLite 只用于开发测试，边缘节点是 00 G4）。
9. **只读查询接口**：库存查询、流水、占用明细、对账差异（原文档 §6.2"库存"组）。

## 3. 领域模型

### 3.1 数量值对象 `Quantity`

- 内部只存整数 `milli: int`，单位是 SKU `base_uom` 的 1/1000。KG 计的 SKU 就是克，PCS 计就是 0.001 个。
- **入参**：只收字符串，正则 `^-?\d{1,15}(\.\d{1,3})?$`。超过 3 位小数、科学计数法、空串、JSON number 一律 **400**，不四舍五入（错误码见 §7.5）。
- **出参**：固定 3 位小数字符串，如 `12500 → "12.500"`，`-2000 → "-2.000"`。单位取 `sku.base_uom`，接口里单独返回 `uom` 字段。
- **换算**：作业单位（箱）→ 基本单位只在入口做一次（原文档 §3.3）：`base_milli = parse_milli(qty) × base_qty_milli / 1000`，`base_qty_milli` 是 1 个作业单位折合的基本单位量（milli 整数，第 1 篇 #8 由 `ratio_to_base` 改名）。如果结果不是整数 milli，返回 400，不取整。
- 绝不经过 `float`。原文档 §4.3 示例里的 `bindparams(qty=float(qty))` 作废，改为绑定 `int`。
- 取值范围：`BIGINT` 上限约 9.2×10^18 milli，远超业务量。JSON 输出用字符串，不受 JS 2^53 限制（原文档 §6.1）。

### 3.2 库存行 `Stock`

```
on_hand        在库总量（物理在库）
allocated      已分配未拣   = Σ ALLOCATE 占用的未结余量
reserved       已预占       = Σ RESERVE  占用的未结余量
quality_hold   质检/盘点冻结 = Σ QUALITY  冻结的未结余量
hold_qty       冻结         = Σ MANUAL + Σ RETURN_PENDING + Σ SCRAP_PENDING + Σ PROCESSING + Σ LIVE_HOLD 的未结余量（列 hold_qty_milli）

available = on_hand − allocated − reserved − quality_hold − hold_qty   （可预占量）
pickable  = on_hand − quality_hold − hold_qty − allocated              （原文档 §3.4，不含 reserved）
book      = on_hand                                                  （盘点基准）
```

列名一律加 `_qty_milli` 后缀，如 `on_hand_qty_milli`。下文为可读性简写。

### 3.3 占用与冻结

- `Reservation(stage, quantity, consumed, released, status)`：未结余量 = `quantity − consumed − released`。`status` 是派生的：余量 > 0 为 `RESERVED`；余量 = 0 时，有消耗为 `CONSUMED`，否则为 `RELEASED`。
- `Hold(hold_type, quantity, released, status)`：未结余量 = `quantity − released`。

### 3.4 流水 `Movement`

`(biz_type, biz_no, line_no, leg, direction, stock_id, hold_id, stock_seq, qty, before, after, PDA 业务键四列)`。只追加，不可修改。`hold_id` 可空：冻结类流水（`PROCESS_CONSUME`、活鲜 `SCRAP`）指向单条 `stock_hold`，其它流水为 NULL。`direction ∈ {−1, 0, +1}`：0 是纯事件（`SHIP`），不改 `on_hand`，不进记账链。

### 3.5 不变量

| # | 内容 | 库层 CHECK | 应用层断言 | 对账任务 |
|---|---|---|---|---|
| I1 | 五列均 ≥ 0 | `ck_stock_nonneg` | 每次原语后 | — |
| I2 | `allocated + reserved + quality_hold + hold_qty ≤ on_hand` | `ck_stock_nonneg` | 每次原语后 | — |
| I2' | 所有数量列都是整数（SQLite 防 REAL/TEXT 混入） | `ck_stock_int` 等 | `Quantity` 类型 | — |
| I3a | `allocated = Σ(ALLOCATE 余量)` | 不能（跨表） | 原语内同事务更新 | 每 5 分钟 |
| I3b | `reserved = Σ(RESERVE 余量)` | 不能 | 同上 | 每 5 分钟 |
| I3c | `quality_hold = Σ(QUALITY 余量) + Σ(RETURN_QC 余量)` | 不能 | 同上 | 每 5 分钟 |
| I3d | `hold_qty = Σ(MANUAL 余量) + Σ(RETURN_PENDING 余量) + Σ(SCRAP_PENDING 余量) + Σ(PROCESSING 余量) + Σ(LIVE_HOLD 余量)` | 不能 | 同上 | 每 5 分钟 |
| I3e | 每条 `RETURN_QC` 明细：`released_qty_milli = Σ stock_hold_release.qty_milli + Σ 子明细.hold_qty_milli（from_hold_id = 本行 id）`；不等说明有人绕过 `release_qc_hold` / `convert_hold` 直接 UPDATE 释放（小赵 S6）。部分转换可以有多条子明细，不再用 `op_key = 'CVT:' \|\| id`（那一列只能对上一次全量转换，而且会和 `from_hold_id` 重复计数）。另查**误报回转**：`is_reversal = true` 的明细，其 `from_hold_id` 必须指向同 `stock_id`、已 RELEASED 的 `SCRAP_PENDING` | 不能 | 同上 | 每 5 分钟 |
| I3f | 每条 `PROCESSING` 明细：`released_qty_milli = Σ stock_hold_release.qty_milli（本行）+ Σ stock_movement.move_qty_milli（hold_id = 本行，biz_type = PROCESS_CONSUME，direction = −1）`。同一 stock 可以有多条 `PROCESSING`，按单条冻结对账，不按 stock 汇总 | 不能 | 原语内同事务 | 每 5 分钟 |
| I3g | 每条 `LIVE_HOLD` 明细：`released_qty_milli = Σ stock_hold_release.qty_milli（本行）+ Σ stock_movement.move_qty_milli（hold_id = 本行，biz_type = SCRAP，direction = −1）`。死亡和日失重写的是 `SCRAP`，靠 `hold_id` 与普通报损分开 | 不能 | 原语内同事务 | 每 5 分钟 |
| I4 | 每行 `on_hand = Σ(该 stock_id 流水 qty × direction)`；按仓汇总同理 | 不能 | — | 日终 + 抽样 |
| I5 | 每条流水 `after = before + qty × direction` | `ck_mv_balance` | 写流水前 | — |
| I5' | 每行记账链连续：第 n 条的 `before` = 第 n−1 条的 `after`，`stock_seq` 从 1 连续无缺号 | 唯一性：`uq_mvk_stock_seq` | — | 每 5 分钟（增量） |
| I6 | 同维度只有一行 `stock` | `uq_stock_dim`（0 哨兵） | — | — |
| I7 | 单据未完成时，其占用不能被提前清零（原文档 I7） | 不能 | 由各单据模块断言 | 每 5 分钟 |
| I8 | 占用/冻结：`consumed + released ≤ quantity` | `ck_res`、`ck_hold` | — | — |
| I9 | 占用/冻结的 `status` 由余量决定 | `ck_res_status`、`ck_hold_status` | — | — |
| I10 | 流水只追加；一行单据只有一种记账来源，PDA 行只有持有设备能记账 | 权限 + 触发器 | repository 只暴露 insert | — |

应用层断言放在 `domain/invariants.py`。CI 中用 hypothesis 生成随机原语序列（含并发交错），每步后校验 I1–I8（原文档 §4.1）。

## 4. 涉及的表（字段、约束、索引）

完整 DDL 在 `wms-design/sql/schema/`，库存表在 `02_inventory.sql`。`schema_sqlite.sql` 由 `verify_sqlite.py` 按加载顺序机械生成，翻译改动仍然只有 4 类。`schema_postgres.sql` 只是指针，不要把 DDL 写回去。下面列关键字段。

### 4.1 `stock`

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT PK | 应用层生成（R1） |
| warehouse_id / location_id / sku_id / lot_id | BIGINT NOT NULL | |
| container_id | BIGINT NOT NULL DEFAULT 0 | 0 = 散货（R11） |
| uom | VARCHAR(16) | 恒等于 `sku.base_uom` |
| on_hand_qty_milli / allocated_qty_milli / reserved_qty_milli / quality_hold_qty_milli / hold_qty_milli | BIGINT NOT NULL DEFAULT 0 | |
| ledger_seq | BIGINT NOT NULL DEFAULT 0 | 每改一次 `on_hand` 加 1，与流水 `stock_seq` 对应 |
| version | BIGINT | 每次 UPDATE 加 1（观测与乐观展示用，不参与判断） |

约束：`uq_stock_dim`、`ck_stock_container`、`ck_stock_int`（`x = CAST(x AS BIGINT)`）、`ck_stock_nonneg`（I1+I2）。
索引：`ix_stock_sku_avail (sku_id, warehouse_id, lot_id) WHERE on_hand_qty_milli > 0`（FEFO 候选）、`ix_stock_loc`、`ix_stock_wh`。

### 4.2 `stock_reservation`

| 字段 | 说明 |
|---|---|
| stage | `RESERVE` / `ALLOCATE`，CHECK |
| source_type / source_id / source_line_id | `source_line_id NOT NULL DEFAULT 0`（R11） |
| op_key VARCHAR(80) UK | 占用操作幂等键，如 `RES:{outbound_code}:{line_no}:{attempt}` |
| reserve_qty_milli / consumed_qty_milli / released_qty_milli | `ck_res`：`reserve > 0`，`consumed + released ≤ reserve` |
| op_key | **`RES:{doc_no}:{line_no}:{alloc_round}:{stock_id}`**，`uq_res_op` 唯一。`alloc_round` 存在出库行上（第 4 篇），每次重新分配 +1；同一轮分配重试时键不变，按幂等返回已有占用；重新分配是新的一轮，不会撞到旧占用。一轮分配拆到多行库存时，`stock_id` 区分每一条 |
| status | `RESERVED / CONSUMED / RELEASED`，**由余量决定**（`ck_res_status`）：余量 > 0 ⇔ `RESERVED`；余量 = 0 时有消耗为 `CONSUMED`，否则 `RELEASED`。过期任务按 `status = 'RESERVED'`（`ix_res_exp`）扫描，不会漏掉还占着量的记录，也不会扫到已结清的 |
| expires_at | 预占过期时间，过期释放（UC8）。第九轮：不传时由库计算 `created_at + 24h`；允许缩短（更早释放更安全），不许超过 `created_at + 24h`（`ck_res_ttl`），不许为 NULL（PG `NOT NULL`；SQLite `trg_res_expires_lock`）；PG 的 `created_at` 由 `trg_res_ttl` 强制为库时钟且不可改（00 §6.8） |

索引：`ix_res_stock (stock_id, stage, status)`、`ix_res_source`、`ix_res_exp WHERE status='RESERVED'`。

### 4.3 `stock_hold`（新增）

`hold_type`、`reason_code`、`source_type/source_id`、`op_key UK`、`hold_qty_milli`、`released_qty_milli`、`status (HELD/RELEASED)`、`operator_id`、`approval_type`、`approval_no`（九轮新增，可空，只有误报回转的 `RETURN_QC` 填写，§7.1.1）、`is_reversal`（BOOLEAN NOT NULL DEFAULT false，误报回转明细的显式标记，小赵 N1）、`from_hold_id`（可空，`convert_hold` 子明细指向父冻结；外键 `fk_hold_from`，`ck_hold_from` 禁止指向自己。部分索引 `ix_hold_from`，**不是唯一**：一条父冻结可以多次部分转出）。

**一套方案：`hold_type` 是大类，决定计入哪一列；`reason_code` 是细分原因，二者成对约束。**

| hold_type | 计入列 | 允许的 reason_code | 谁能冻结 / 解冻 |
|---|---|---|---|
| `QUALITY` | `quality_hold` | `QC_PENDING` 待检、`COUNT_LOCK` 盘点冻结 | 03/08 流程 |

约束：

- `ck_hold_type`：`hold_type IN ('QUALITY','RETURN_QC','MANUAL','RETURN_PENDING','SCRAP_PENDING','PROCESSING','LIVE_HOLD')`。`PROCESSING` / `LIVE_HOLD` 由本篇统一收进这条 CHECK。#12（`docs/18-live-hold`）和 #13（`docs/17-processing`）应删掉各自对 `ck_hold_type` / `ck_hold_reason` / `ck_hold_process` 的改动，改调本篇原语。
- `ck_hold_retqc`：`RETURN_QC` 必须 `source_type = 'QC'`、`source_id > 0`（**质检单头** `inbound_order.id`，不是质检行）、`operator_id = 0`。质检行是 `inbound_line`；报损单上的 `source_id = inbound_line.id` 是第 9 篇的事实，跟本行的 `source_id` 不是同一个 id。
- `ck_hold_approval`（九轮，N1 改为按显式列识别）：`is_reversal = true`（误报回转）⇔ `approval_type = 'SCRAP_MISREPORT'` 且 `approval_no` 非空；其余明细两列必须都为 NULL。`ck_hold_reversal_key`：`is_reversal = (hold_type = 'RETURN_QC' AND op_key 以 CVT: 开头)`，双向一致。PG 用 `LIKE 'CVT:%'`（区分大小写）；SQLite 的 `LIKE` 默认不区分大小写，所以 SQLite 用 `GLOB 'CVT:*'`。`'cvt:'` 在两库都被拒。缺审批、审批类型不对、非回转明细带审批都被拒。应用层先查审批（缺少或类型不对 → 40930），CHECK 是库层兜底。
- `ck_hold_approval_no`（十一轮，十二轮收紧）：`approval_no` 非空时必须是 `APR-{仓库编码}-{yyyyMMdd}-{6 位数字}`，如 `APR-WHSH01-20261015-000001`（`WHSH01` 是 verify 种子仓库的编码）。仓库编码取 `warehouse.code`，字符集**以第 1 篇（#8）为准：`[A-Z0-9]{2,16}`**（2–16 位大写字母或数字，不含 `-` 和 `_`）。月份限 01–12、日限 01–31，并且必须是**真实日历日**（N1，含大小月和闰年，年份不能是 0000）：PG 在正则通过后用 `CASE` 按当月天数比较（不会因 `20260230` 抛转换错误）；SQLite 用 `date(y-m-d) = y-m-d`（`date()` 会把 02-30 规范成 03-02，不等即拒）。`approval_no` 关联真实审批单的外键在 #9（第 12 篇审批表）合并后补上，见 00 §6.6.1。PG 用正则 `^APR-[A-Z0-9]{2,16}-[0-9]{4}(0[1-9]|1[0-2])(0[1-9]|[12][0-9]|3[01])-[0-9]{6}$`。SQLite 先限总长度 **22–36**（`APR-` 4 位 + 编码 2–16 位 + `-yyyyMMdd-NNNNNN` 16 位），再用 `substr` 切分加 `GLOB` 校验：编码段 `NOT GLOB '*[^A-Z0-9]*'`，末 16 位 `-yyyyMMdd-NNNNNN`，月、日各两位分别 GLOB。
- `ck_hold_reason`：类型与原因成对（类型非法时只由 `ck_hold_type` 报，不会两条一起报）。
- `ck_hold_return`：`RETURN_PENDING` 必须 `source_type = 'RETURN_RECORD'`、`source_id` = 待回库记录 id、`operator_id = 0`。`op_key` 固定为 `RRH:{return_record_id}`（与第 4 篇一致）。
- `ck_hold_scrap`：`SCRAP_PENDING` 必须 `source_type = 'SCRAP'`、`source_id` = **第 9 篇报损单 id，不是报损行 id**（小赵 N2 口径 (a)：SCRAP_HANDOVER 同事务先建报损单，不挂待回库记录 id）、`operator_id = 0`。不走 `place_hold`。
- `ck_hold_process`：`PROCESSING` 必须 `source_type = 'PROCESS_ORDER'`、`source_id > 0`、`operator_id = 0`、`op_key` 前缀 `PRCI:`（PG `LIKE`，SQLite `GLOB`，大小写敏感）。
- `ck_hold_live`：`LIVE_HOLD` 必须 `source_type = 'LIVE_TANK_HOLD'`、`source_id > 0`、`operator_id = 0`。不限制 `op_key` 前缀。
- `trg_hold_immutable`（两库，小赵 N1）：`stock_hold` 写入后只允许改 `released_qty_milli`、`status`、`version`、`updated_at`（表上没有 released_at/released_by 列，释放人和时间记在调用方单据与审计里，不需要额外放行）；`id/stock_id/hold_type/reason_code/source_type/source_id/op_key/hold_qty_milli/operator_id/approval_type/approval_no/is_reversal/from_hold_id/created_at` 改了就报 `hold_immutable`。类型转换只走 `convert_hold`（关旧建新），否则先把 `SCRAP_PENDING` 改成 `MANUAL` 就能绕过 40933。PG 另有列级授权：`wms_app` 对 `stock_hold` 只有 `UPDATE (released_qty_milli, status, version, updated_at)`。
- **只能沿释放方向变**（小赵 R1）：`trg_hold_immutable` 另拒 `NEW.released_qty_milli < OLD.released_qty_milli`（释放量只增不减）和 `OLD.status = 'RELEASED' AND NEW.status <> 'RELEASED'`（已释放不能回 HELD）。这两列在 PG 列级授权里是放行的，所以 `wms_app` 也靠这个触发器拦住，不然改回 HELD 后再走一次释放原语，`stock.hold_qty_milli` 会被多减一次 q，减掉的是同行别的冻结量。
- **不可删除、不可 REPLACE**（小赵 R2）：
  - PG：`trg_hold_no_delete`（`BEFORE DELETE`，行级）与 `trg_hold_no_truncate`（`BEFORE TRUNCATE`，语句级）报 `hold_immutable`。`wms_app` 本来就没有 DELETE/TRUNCATE 权限（`permission denied`），触发器兜底超级用户和迁移脚本，与流水表写法一致。PG 的 `ON CONFLICT DO UPDATE` 走 UPDATE 触发器和列级授权，不需要另外处理。
  - SQLite：`trg_hold_no_delete`（`BEFORE DELETE`）报 `hold_immutable`。`INSERT OR REPLACE`/`REPLACE` 冲突时会先删旧行，但默认 `recursive_triggers = OFF`，这次删除**不触发** DELETE 触发器。两种办法都实测过：① `PRAGMA recursive_triggers = ON` 后 REPLACE 会撞上 DELETE 触发器，但这是**连接级**开关，每个连接都要设，漏一个就失效；② `trg_hold_no_replace`（`BEFORE INSERT`，`WHEN EXISTS (… h.id = NEW.id OR h.op_key = NEW.op_key)`）报 `hold_duplicate`，冲突检查之前就中止，REPLACE 走不到删除那一步，写在 schema 里，库级生效。**采用 ②**。代价是 SQLite 上 `convert_hold` 等重试撞的是 `hold_duplicate`，PG 上撞的是 `uq_hold_op`（23505），两者都走"按 `op_key` 查回已有明细"的幂等分支；`stock_hold` 的写入一律用普通 `INSERT`，不用 `ON CONFLICT DO NOTHING`/`OR IGNORE`（BEFORE INSERT 触发器先于冲突处理，会直接报错）。
- `uq_hold_return (source_id) WHERE hold_type = 'RETURN_PENDING'`（PG、SQLite 都是部分唯一索引）：一条待回库记录最多一条 `RETURN_PENDING` 冻结。**只约束 `RETURN_PENDING`**，`convert_hold` 转出的报损明细（`SCRAP_PENDING/SCRAP`，`source_type = 'SCRAP'`，不用 `RETURN_RECORD`）不受它约束（小赵二轮 D1）。
- `ck_hold`：`0 ≤ released ≤ hold`；`ck_hold_status`：**状态由余量决定**，`HELD ⇔ released < hold`，`RELEASED ⇔ released = hold`。
- 新增原因走迁移，各模块在自己的文档里登记。

**列名统一**：`stock` 上的冻结汇总列改名为 **`hold_qty_milli`**（原 `frozen_qty_milli`，与 00/04 的写法一致），`= Σ MANUAL + Σ RETURN_PENDING + Σ SCRAP_PENDING + Σ PROCESSING + Σ LIVE_HOLD` 的余量。`v_stock_available.available_qty_milli = on_hand − allocated − reserved − quality_hold − hold_qty`，所以 `RETURN_PENDING`、`PROCESSING`、`LIVE_HOLD` 冻结的量**直接从可用量扣除，FEFO 候选查询（`available > 0`）分不到**。验证脚本两库各一条断言：把 stock 12 的可用量全部 RETURN_PENDING 冻结后，available 从 20000 变成 0，FEFO 候选从 4 行变成 3 行且不含 12（事务内验证后回滚）。另有 stock 46（`PROCESSING` 5000）、stock 47（`LIVE_HOLD` 3000）可用量都是 0，不进入 FEFO 序列。

**盘点口径**（第 8 篇负责，本篇只引用）：`RETURN_PENDING` 冻结的货账面在原库位、实物在分拣员手上。盘点算差异时，这部分要从账面量里扣掉，**不能生成盘亏调整**；由待回库闭环（confirm / 就近放回）来消掉。

**`stock_hold_release`（新增，A3）**：冻结部分释放的操作去重，`(id, hold_id FK fk_hr_hold → stock_hold, op_key UK uq_hr_op, qty_milli, created_at)`，只追加：PG 拒 UPDATE/DELETE（行级触发器）和 TRUNCATE（`trg_hr_no_truncate`，小赵 S5），`wms_app` 只授 `SELECT, INSERT`；SQLite 拒 UPDATE/DELETE，并用 `trg_hr_no_replace`（BEFORE INSERT，`id` 或 `op_key` 已存在 → `hold_duplicate`）挡住 `INSERT OR REPLACE`/`REPLACE`/UPSERT（小赵 Q1，原因同 §4.3 R2：REPLACE 删旧行不触发 DELETE 触发器，去重记录被冲掉后重放会再释放一次）。`release_qc_hold`、`release_hold` 每次释放写一行，`release_live_hold` 按池内每条明细写一行。调用方传 `op_key`（质检通过用 `QCR:{inbound_line_id}:{op_seq}`，整池解锁用 `LTH:{live_tank_hold_id}:{release_inspection_id}:{hold_id}`）。重放同一 `op_key` 在 PG 撞 `uq_hr_op`、在 SQLite 撞 `hold_duplicate`，整个事务回滚（§7.1.3、§7.1.5、§7.1.7）。`consume_process_hold` 和 `consume_live_hold` 不写这张表，幂等靠流水去重键。`hold_id` 外键保证释放记录挂在真实冻结上（小赵 S6）；绕过本表直接 UPDATE 释放 `RETURN_QC` 由 I3e 对账发现（§3.5）。

### 4.4 `stock_movement`、`stock_movement_key`、`stock_ledger_line`

**设计前提：单仓单写库**（00 总体设计 §6.1a）。每个仓只有一个权威写库：一期中心 PG，SQLite 只用于开发和测试；是否做边缘节点是 00 的待定问题 G4（Yuri 定范围）。本篇的所有唯一性和记账链都只在**一个库内**成立，不处理两个库之间的去重合并。

#### 4.4.1 `stock_movement`（流水主表，只追加）

| 字段 | 说明 |
|---|---|
| biz_type / biz_no / line_no | 业务单据行。`biz_no` 带单据类型前缀，全局唯一。`biz_type` 无 CHECK，注释登记 `RECEIVE/PUTAWAY/PICK/REVERSE_PICK/SHIP/MOVE/ADJUST/COUNT/RETURN/SCRAP/CROSS_DOCK/OPENING`，另加第 17 篇的 `PROCESS_ISSUE` / `PROCESS_CONSUME` / `PROCESS_OUTPUT` / `PROCESS_REVERSE`。`consume_process_hold` 记 `PROCESS_CONSUME` |

PK `(id, occurred_at)`：PG 侧 `PARTITION BY RANGE (occurred_at)` 按月分区，分区表的主键必须带分区键。`id` 是雪花 ID，全局唯一由去重表的 `movement_id PK` 保证。

#### 4.4.2 `stock_movement_key`（记账去重表，不分区）

**为什么单独一张表**：PG 分区表上的唯一约束必须包含分区键，只能保证**分区内**唯一。同一个键 10-31 写一次、11-01 再写一次会落进两个分区，两条都能写进去。所以所有业务唯一键放到这张**不分区**的表里，与流水**同一事务**写入，撞任一唯一键整个事务回滚。验证脚本有"跨分区重复"断言（10-31 与 11-01 同键，第二笔被拦且流水随之回滚）。

| 唯一键 | 列 | 条件 | 防什么 |
|---|---|---|---|
| `movement_id` PK | = 流水 id | — | 跨分区 id 唯一 |
| `uq_mvk_idem` | idempotency_key | — | 同一操作重复过账 |
| `uq_mvk_biz_line` | (biz_no, line_no, op_no, leg) | `src_kind = 'DOC'` | DOC 单据行同一次操作重复过账 |
| `uq_mvk_pda_op` | (src_task_id, src_line_no, device_instance_id, src_op_seq, leg) | `src_kind = 'PDA'` | PDA 同一操作重复过账，包括 `Idempotency-Key` 过期后的重放 |
| `uq_mvk_stock_seq` | (stock_id, stock_seq) | `direction <> 0` | 记账链分叉 |

占用（`stock_reservation.op_key`）不是记账键，格式见 §4.2：`RES:{doc_no}:{line_no}:{alloc_round}:{stock_id}`。

**`idempotency_key` 只有一种格式**：

```
{biz_no}:{line_no}:{op_ref}:{leg}
op_ref = D{op_no}                          （DOC）
       = P{device_instance_id}.{op_seq}    （PDA）
例：ADJ-WHSH01-0003-20261015-000012:1:D2:1
    PK-WHSH01-0003-20261015-000842:3:PDEV-7f3a.2:1
```

**流水与 key 行在库层绑定**（小赵二轮 C2）：`stock_movement` 上有外键 `fk_mv_key (id, idempotency_key, biz_no, line_no, op_no, leg, src_kind, stock_id, stock_seq, direction, occurred_at) → stock_movement_key` 的同名列（被引用键 `uq_mvk_mv`），`DEFERRABLE INITIALLY DEFERRED`，提交时检查。

- 只写流水不写 key 行 → 提交失败；key 行和流水任一列对不上（如 key 写 `RR-1`、流水写 `ADJ-9`）→ 提交失败。所有去重都建在 key 表上，绕不过去。
- 只列 NOT NULL 列：外键是 `MATCH SIMPLE`，任一列为 NULL 会整条跳过检查。PDA 四元组由 `ck_mv_kind`/`ck_mvk_kind` 和 `uq_mvk_pda_op` 管。
- **为什么用外键而不是触发器**：PG 11 起分区表可以作为外键的引用方指向普通表，`stock_movement` 是分区表这一点不受限；外键在两库语义一致，比各写一份触发器少一处分叉。代价是 key 表多一个唯一索引（PG 索引总数 114 → 115）。
- SQLite 外键要求**每个连接** `PRAGMA foreign_keys = ON`（默认关），连接工厂必须设置，启动自检读一次该 pragma，为 0 拒绝启动。
- 反方向（有 key 行没流水）不约束：两者同事务写入，事务回滚时一起消失。

它和两个业务唯一键表达的是同一件事，三者同时存在只是为了"按字符串查"和"按字段约束"两种用法。**同一行的第二次合法操作不会被吞**：DOC 的 `op_no` 不同，PDA 的 `op_seq` 不同，键就不同（验证脚本里两种来源各有一条断言）。原来 §4.4、§8.4 和验证种子里的三种写法作废。

#### 4.4.3 `stock_ledger_line`（单据行记账来源归属）

`PK (biz_no, line_no)`，`src_kind`，`owner_device_instance_id`（PDA 行当前唯一允许记账的设备实例），`post_count`。

- **一行单据只能有一种记账来源**：第一次记账时**先查再插**占位（`INSERT … SELECT … WHERE NOT EXISTS (同 biz_no, line_no) ON CONFLICT DO NOTHING`；第十二轮起 SQLite 有 `trg_sll_no_replace`，裸 `ON CONFLICT DO NOTHING` 的重放会被它拦成 `ledger_line_duplicate`，见 00 §6.10 第 8 条），之后每次记账条件更新 `post_count = post_count + 1 WHERE src_kind = :kind AND (owner_device_instance_id IS NULL OR owner_device_instance_id = :dev)`，影响 0 行就拒绝（`40930`）。PK 保证两种来源并发抢第一次时只有一个能占位。
- **来源不可改**（小赵二轮 C3）：`trg_sll_immutable`（`BEFORE UPDATE`，两库各一份）禁止修改 `src_kind`、`biz_no`、`line_no`，报 `ledger_line_immutable`；换主只能改 `owner_device_instance_id`、`post_count`、`updated_at`。PG 侧 `wms_app` 在这张表上只有 `SELECT, INSERT` 和这三列的列级 `UPDATE`，见 §4.4.4。
- **库层兜底**：`stock_movement_key` 上的 `BEFORE INSERT` 触发器 `trg_mvk_line_kind` 要求归属行存在、来源一致，PDA 行还必须是当前持有设备，否则报 `ledger_line_owner_mismatch`。两库各一份，语义相同。
- 换设备见 §8.4。

**去重记录与 outbox 清理**（小赵 Q2，PM 已定）：

- `wms_app` 对 `idempotency_record`、`outbox_event` 没有 DELETE/TRUNCATE，否则能删掉未过期的去重记录（不记库存的写接口重放会重新执行）或未投递的事件（直接丢失）。
- 清理函数 `public.purge_expired()`：`SECURITY DEFINER`，固定 `SET search_path = pg_catalog, public, pg_temp`（第九轮：pg_temp 显式且最后，00 §6.9），表名全部 schema 限定；**不接受参数**，删除条件写死，**按库内 UTC 比较**（十轮 P1）：`idempotency_record` 只删 `expires_at < (now() AT TIME ZONE 'UTC')`，`outbox_event` 只删 `status = 'SENT' AND sent_at < (now() AT TIME ZONE 'UTC') − 7 天`（保留期 7 天），`PENDING`/`FAILED` 一律不删。返回 `(idem_deleted, outbox_deleted)`。
- 属主 `wms_purge_owner`：`NOLOGIN NOSUPERUSER`，只有这两张表的 `SELECT, DELETE`。`REVOKE EXECUTE … FROM PUBLIC`，只 `GRANT EXECUTE` 给 `wms_cleaner`；`wms_cleaner` 对任何表都没有权限，直接 DELETE 报 `permission denied`。定时任务用 `wms_cleaner` 连接执行 `SELECT * FROM purge_expired()`。
- **时间一律按 UTC 存**（十轮 P1，大肥鱼定）：两表的 `created_at`、`expires_at`、`next_retry_at`、`sent_at` 是不带时区的 `TIMESTAMP`，语义固定为 UTC；PG 默认值改为 `now() AT TIME ZONE 'UTC'`，应用连接固定 `TimeZone = UTC` 写入。清理函数和删除守卫都和 `now() AT TIME ZONE 'UTC'` 比较，与调用方会话时区无关，`wms_cleaner` 改 `TimeZone` 不能放宽窗口。SQLite 的 `datetime('now')` 本身就是 UTC，与进程时区无关。verify：PG 在会话时区 UTC+8 / UTC−10 / UTC+14 下各调一次 `purge_expired()`，删的行数相同（都只删已过期那条）；+14 下超级用户删还剩 12 小时的记录被 `purge_not_allowed` 拦；SQLite 在进程时区 +8 / −10 下清理行数相同。
- **过期列只许往后改**（十轮 P2）：两库 `trg_idem_expiry_fwd`/`trg_outbox_expiry_fwd`（BEFORE UPDATE）报 `expiry_backdate`：`expires_at` 不能调小；`sent_at` 写入后不能调小、不能清空，首次写入不得早于 `created_at`（挡 PENDING → SENT 时倒填 2000-01-01）；**变成 SENT 的那次写入 `sent_at` 必须等于当前 UTC 时间，容差 ±5 秒**（十五轮 R1，`sent_at_not_now`；PG 比对 `now() AT TIME ZONE 'UTC'`，SQLite 比对 `julianday('now')`，过去或将来的时间都拒；这条检查先于“不早于 created_at”，倒填 2000-01-01 现在报 `sent_at_not_now`）；`SENT` 是终态，不能退回；两表 `created_at` 不可改。所以 `wms_app` 不能先 UPDATE 把活记录"改成已过期"再让清理删掉。
- **应用只能插入 PENDING**（十六轮 R1，第八轮改为按表属主判断）：否则应用可以直接以 `SENT` 加倒写的 `sent_at` 插入，绕过 `sent_at_not_now`（那条只管 UPDATE），再让清理提前删掉。`wms_app` 是 `NOLOGIN`，应用连接的是继承它的登录角色，`current_user` 不是 `wms_app`，按角色名判断不会生效。PG 的 `trg_outbox_insert_pending`（BEFORE INSERT）改为：当前用户不是 `outbox_event` 的表属主时，`status` 必须是 `PENDING` 且 `sent_at IS NULL`，否则报 `outbox_insert_not_pending`（42501）。非 `PENDING` 的值直接拒绝，不改写成 `PENDING`。表属主（建表的超级用户或迁移角色）可以插入其他状态，种子和迁移走这条。**SQLite 没有角色，SQLite 端的应用只能插入 `PENDING`**：同名触发器对所有 INSERT 生效，`FAILED` 同样拒绝；验证脚本造清理测试需要的 SENT 种子时，走单独的种子路径，临时 DROP 该触发器，写完按 `sqlite_master` 里的原文重建，并断言已重建。
- **触发器函数固定 search_path**（第八轮）：本篇定义的 9 个触发器函数都加 `SET search_path = pg_catalog, public`（第九轮起改为 `pg_catalog, public, pg_temp`，见 00 §6.9）。它们不是 `SECURITY DEFINER`，按调用方身份执行。不钉的话，登录角色把 `search_path` 设成自己的 schema 在 `pg_catalog` 前面，就能用同名表、同名 `now()`、同名 `=(date,date)` 改写触发器看到的对象。钉住之后：`trg_mvk_line_kind` 里未限定的 `stock_ledger_line` 只解析到 `public`；`trg_expiry_forward` 和 `trg_purge_guard` 的 `now()`、`extract`、`interval`、`AT TIME ZONE` 走 `pg_catalog`；`trg_lot_sell_deadline` 的 `IS DISTINCT FROM` 用 `pg_catalog` 的日期等号。`trg_sll_immutable`、`trg_hold_immutable`、`trg_hold_no_delete`、`trg_append_only` 的函数体只看 `NEW`/`OLD`/`TG_*`，没有名字查找，同样钉住。`purge_expired()` 原本已经是这个 `search_path`，这一轮不改函数体。
- **SENT 必带 sent_at**（十轮 P3）：`ck_outbox_sent CHECK (status <> 'SENT' OR sent_at IS NOT NULL)`。
- 库层兜底（两库，条件与函数一致）：PG `trg_idem_purge_guard`/`trg_outbox_purge_guard`（BEFORE DELETE，行级）和 `trg_idem_no_truncate`/`trg_outbox_no_truncate`（BEFORE TRUNCATE）报 `purge_not_allowed`，拦超级用户和迁移脚本；条件用 `COALESCE(<条件>, false)`（SQLite `COALESCE(<条件>, 0)`），NULL 比较不再漏过（十轮 P3）；SQLite 同名 BEFORE DELETE 触发器，另加 `trg_idem_no_replace`/`trg_outbox_no_replace`（BEFORE INSERT，主键已存在 → `idem_duplicate`/`outbox_duplicate`），挡 REPLACE 删旧行。SQLite 上应用把 `idem_duplicate` 当作「键已存在」，与 PG 的 23505 走同一分支；写入用普通 `INSERT`，不用 `OR IGNORE`/`ON CONFLICT DO NOTHING`。
- 残留风险：`wms_app` 仍能 UPDATE 这两张表（业务需要改 `status`/`retry_count`），理论上可以先把 `expires_at` 改早再等清理；这属于应用代码路径，由 repository 只暴露业务字段更新来约束，不在库层再拦。

**新表必须授权**：`public` 下每张表和视图都必须对 `wms_app` 有显式 GRANT（按最小权限，不给 TRUNCATE），写在该表所在的 `sql/schema/NN_*.sql` 末尾（`-- @pg-only`）。不要写回 `schema_postgres.sql`。`verify.sh` 按**期望权限矩阵**逐表核对（小赵 S4）：遍历 `public` 下所有表（含分区父表、不含分区子表）、视图、物化视图和序列（序列查 `USAGE`），对每个对象算出 `wms_app` 实际拥有的 `SELECT/INSERT/UPDATE/DELETE/TRUNCATE` 组合，与脚本里的期望矩阵（即上表）逐项比对。少给、多给（比如 DELETE、TRUNCATE）、漏登记的新表都会失败，并打印差异。列级 UPDATE（`stock_hold`、`stock_ledger_line`）不计入表级矩阵，另有专门断言。SQLite 没有角色，不适用。

**`stock.hold_qty_milli` 只能经原语改**（小赵 N1）：它是 `MANUAL + RETURN_PENDING + SCRAP_PENDING + PROCESSING + LIVE_HOLD` 明细余量的汇总，必须和明细在同一事务里变（`hold`/`unhold`/`release_return_hold`/`release_scrap_hold`/`post_out` 等，§7.1）。保障分三层：① 代码层：只有库存原语模块持有 `stock` 的写 SQL，CI 静态检查禁止原语模块以外出现 `UPDATE stock … hold_qty_milli`；② 库层：明细侧由 `trg_hold_immutable` + PG 列级授权保证明细量/类型不可改，所以汇总列只能跟着原语的释放/新建走；`stock` 行本身不加列级限制，因为扣减、占用原语都要更新同一行；③ 对账：I3d 每轮比对 `hold_qty_milli = Σ 明细余量`，不等即告警（§9）。SQLite 没有角色和列级授权，靠 ① + `trg_hold_immutable` + I3d；SQLite 只在边缘单进程内使用，只有 WMS 服务进程持有库文件。

归档：PG 按分区 `DETACH`（DDL，需要 DBA 权限，不经过行触发器）；SQLite 导出后由维护脚本"删触发器 → 删行 → 重建触发器"，全程写审计。这是唯一允许的删除路径，且不在应用里。验证脚本断言：两库 UPDATE/DELETE 都被触发器拦下；PG 的 `wms_app` 收到 `permission denied`。

## 6. 核心流程

### 6.1 原语的统一事务模板

所有改 `on_hand` 的原语都是同一个模板，**一个事务内**：

1. **来源归属**（§4.4.3）：`INSERT stock_ledger_line … SELECT … WHERE NOT EXISTS … ON CONFLICT DO NOTHING`（先查再插），再条件更新 `post_count`（来源/设备不符 → 回滚，`40930`）。
2. **条件 UPDATE `stock`**：把校验写进 WHERE，包括可用量、以及**库位未被盘点锁定**（`AND EXISTS (SELECT 1 FROM location l WHERE l.id = stock.location_id AND l.status <> 'LOCKED')`，§8.1）。同时 `ledger_seq = ledger_seq + 1`，用 `RETURNING on_hand_qty_milli, ledger_seq` 拿回新值（PG 支持；SQLite ≥ 3.35 支持，00 启动自检强制）。这是数据库返回的写后值，**不是先读后判断**。
3. `rowcount == 0` → 回滚，再做一次**只读分类**决定返回哪个码（库位锁定 `40906`，可用量不足 `40902/40904`）。分类读只用于报错，不用于判断能不能扣。
4. 写流水 `stock_movement`：`after` = 返回值，`before = after − qty × direction`，`stock_seq` = 返回的 `ledger_seq`。
5. 写去重键 `stock_movement_key`：撞任一唯一键 → 整个事务回滚（重复过账，§8.3）。
6. 应用层断言 I1/I2/I5 → 提交。

```mermaid
      INV->>INV: 断言 I1/I2/I5
      INV->>DB: COMMIT
    end
  end
  API-->>PDA: 200 {line_status, next_line, ...}
```

要点：

- **水位线解决在途单据**：快照记的是每行的 `ledger_seq`。回放只累加 `stock_seq ≤ 水位线` 的流水，所以对账期间新提交的拣货不会造成假差异。不用流水 `id` 当水位线，因为 id 由号段生成，多实例之间不单调。

- 占用对账（I3a–d）在同一个读快照里，比较 `stock` 四列与明细表余量汇总。
- 流水归档（PG 按月分区、SQLite 按月导出）之后，回放从"上一份已验证快照 + 之后的流水"开始，不必从头扫全表。
- 全仓 I4（按仓汇总）每天跑一次；按行增量校验（只校验当天 `ledger_seq` 有变化的行）每 5 分钟跑一次。

### 6.5 移库（UC2 / UC15）

一个事务：来源行条件扣减（`on_hand − allocated − reserved − quality_hold − hold_qty ≥ q`，也就是只能移可用量）→ 目标行 upsert（不存在就插一行 0 库存，`uq_stock_dim` 冲突时说明并发插入，重查 id 后继续）→ 目标行 `on_hand += q` → 写两条流水，`leg = 1/2`。两行按 `stock_id` 升序加锁（原文档 §4.3 纪律 2）：先执行 id 较小那一行的 UPDATE。

#### 7.1.1 `convert_hold`：冻结类型转换（小赵二轮 D1）

用途：待回库 SCRAP_HANDOVER（04 §7.3）把 `RETURN_PENDING` 冻结转成报损冻结。原写法"先 `hold` 报损、再 `unhold` 待回库"走不通：`hold` 要求 `available ≥ q`，而这部分量本来就不在可用量里，`available = 0` 时影响 0 行；有别的可用量时又会冻到别的货上（冻了 2q）。

语义：同一事务里按调用方传入的 **qty** 扣原冻结的剩余量（`released += q`；只有 `released = hold` 时状态才变成 `RELEASED`，部分转之后父行仍是 `HELD`），并新建一条数量为 q、同 `stock_id`、`from_hold_id` = 父行的目标类型明细。**不走可用量检查**。全量转换就是 `q = 剩余量`。同一父行可以用不同 `op_key` 转多次，直到剩余为 0。允许的转换（白名单，其余返回 40930，`detail = {from_hold_type, to_hold_type}`）：

| 原类型 → 目标类型 | 汇总列 | `stock` 行 |
|---|---|---|
| `RETURN_PENDING` → `SCRAP_PENDING`（SCRAP_HANDOVER）以及其他 `hold_qty` 列内转换 | 同列 | 一列都不改，`version` 不变 |
| `QUALITY` → `SCRAP_PENDING`、`RETURN_QC` → `SCRAP_PENDING`（质检不合格报损，A3） | 跨列：`quality_hold` → `hold_qty` | 同事务 `quality_hold −q、hold_qty +q`，`version +1` |
| `SCRAP_PENDING` → `RETURN_QC`（报损误报回转，九轮）：**必须**带 `approval_type = 'SCRAP_MISREPORT'` 的审批单号，缺少或类型不对 → 40930 | 跨列：`hold_qty` → `quality_hold` | 同事务 `hold_qty −q、quality_hold +q`，`version +1` |

原来"只允许同一汇总列内转换"和不合格报损冲突：`QUALITY`/`RETURN_QC` 计入 `quality_hold`，`SCRAP_PENDING` 计入 `hold_qty`。可行做法是在同一事务里把 q 从一列挪到另一列：`UPDATE stock SET quality_hold_qty_milli = quality_hold_qty_milli − :q, hold_qty_milli = hold_qty_milli + :q, version = version + 1 WHERE id = :stock_id AND quality_hold_qty_milli >= :q`。可用量 `on_hand − allocated − reserved − quality_hold − hold_qty` 里两列都被减，所以**可用量和冻结总量（quality_hold + hold_qty）都不变**，`ck_stock_nonneg` 不受影响，I3c、I3d 同时成立。这条 UPDATE 影响 0 行说明 I3c 不平：整个事务回滚，返回 `50010`。不合格报损的顺序：第 9 篇先建 DRAFT 报损单，再在同一事务里 `convert_hold(hold_id, q, 'SCRAP_PENDING', ('SCRAP', 报损单 id, 'SCRAP'), op_key)`。一次判完传 `q = 剩余量`、`op_key = CVT:{hold_id}`；质检行分次判不合格时 `q` 是本次数量、`op_key = CVT:{inbound_line_id}:{op_seq}`（与 09/10 一致）。`q` 大于剩余 → 条件更新 0 行 → `40905`。反方向只开放 `SCRAP_PENDING` → `RETURN_QC` 一条（误报回转，见下），转 `QUALITY` 及其他从 `hold_qty` 列转出仍返回 40930。

**误报回转**（九轮）：报损待处置的货被判定误报时，凭 `SCRAP_MISREPORT` 审批把 `SCRAP_PENDING` 剩余量转回 `RETURN_QC` 重新质检，不直接回可售。同一事务内：① 应用层校验审批单存在、类型为 `SCRAP_MISREPORT`（否则 40930，`detail = {from_hold_type, to_hold_type, approval_type}`）；② 新建质检单（第 3/10 篇）；③ 关闭原 `SCRAP_PENDING`；④ 插入 `RETURN_QC`（`reason_code = 'RETURN_QC'`、`source_type = 'QC'`、`source_id` = 新质检单 `inbound_order.id`、`operator_id = 0`、`from_hold_id` = 原 `SCRAP_PENDING`、`op_key` 由调用方传且以 `CVT:` 开头——全量回转用 `CVT:{原 hold_id}`、`is_reversal = true`、带审批两列）；⑤ `UPDATE stock SET hold_qty_milli = hold_qty_milli − :q, quality_hold_qty_milli = quality_hold_qty_milli + :q, version = version + 1 WHERE id = :stock_id AND hold_qty_milli >= :q`（0 行 → 回滚 + 50010）。可用量和冻结总量都不变。之后只能走 `release_qc_hold` 或再次不合格报损。对应报损单由第 9 篇在同一事务里关闭（REVOKED 以外的状态，交接单同样适用，不经过 `release_scrap_hold`）。

```sql
-- PG（SQLite 相同，只是没有 FOR UPDATE：单写者，BEGIN IMMEDIATE 拿写锁）
BEGIN;
-- 0. 读出 stock_id，不加锁。不存在 → 40905。hold_type / stock_id 写入后不可改。
SELECT stock_id FROM stock_hold WHERE id = :hold_id;
-- 1. 先锁库存行，再锁冻结明细，都按 id 升序。同列转换不改数量，也要先锁 stock，
--    避免和 release/consume 交叉等待（§8.2）。SQLite 去掉 FOR UPDATE。
SELECT id FROM stock WHERE id = :stock_id ORDER BY id FOR UPDATE;
SELECT stock_id, hold_type, hold_qty_milli - released_qty_milli AS remain
  FROM stock_hold WHERE id = :hold_id ORDER BY id FOR UPDATE;   -- 不存在、已 RELEASED、或 :q > remain → 40905
-- 应用层：目标不在白名单 → 40930，detail = {from_hold_type, to_hold_type}
UPDATE stock_hold
   SET released_qty_milli = released_qty_milli + :q,
       status = CASE WHEN released_qty_milli + :q = hold_qty_milli THEN 'RELEASED' ELSE 'HELD' END,
       version = version + 1, updated_at = now()
 WHERE id = :hold_id AND status = 'HELD'
   AND hold_qty_milli - released_qty_milli >= :q;   -- 0 行：按调用方 op_key 查子明细，查到则幂等返回，查不到 40905
INSERT INTO stock_hold (id, stock_id, hold_type, reason_code, source_type, source_id,
                        op_key, hold_qty_milli, released_qty_milli, status, operator_id, from_hold_id)
VALUES (:new_id, :stock_id, :to_hold_type, :reason_code, :to_source_type, :to_source_id,
        :op_key, :q, 0, 'HELD', 0, :hold_id);
-- 同列：stock 行不动。跨列（QUALITY/RETURN_QC → SCRAP_PENDING）同事务挪 q，0 行 → 回滚 + 50010
-- 误报回转（SCRAP_PENDING → RETURN_QC）：INSERT 另带 is_reversal=true、
--   approval_type='SCRAP_MISREPORT'、approval_no，source_id = 新 inbound_order.id；挪列方向相反
UPDATE stock SET quality_hold_qty_milli = quality_hold_qty_milli - :q, hold_qty_milli = hold_qty_milli + :q,
       version = version + 1, updated_at = now()
 WHERE id = :stock_id AND quality_hold_qty_milli >= :q;
COMMIT;
```

- **幂等**：`op_key` 由调用方传入，`uq_hold_op` 只保证**这一把键**转一次，不再把键写死成 `CVT:{hold_id}`（那样一条冻结只能转一次，第二次部分转会撞唯一键）。全量转换仍建议用 `CVT:{hold_id}`；分次转换用 `CVT:{行 id}:{op_seq}`。重试时父行条件更新影响 0 行，按调用方 `op_key` 查到已有子明细 → 返回它（200）；查不到 → 余量已被别的路径用掉，返回 40905。同一父行换一把新键可以再转，直到剩余为 0。`op_key` 前缀 `CVT:` 在 PG 用 `LIKE`（区分大小写），SQLite 用 `GLOB`；`'cvt:'` 两库都拒。
- **并发**：先锁 `stock`（`ORDER BY id`），再锁 `stock_hold`（`ORDER BY id`），然后才改明细、插子行；跨列时最后才改数量。同列转换不改 `stock` 的数量和 `version`，但仍先锁库存行，这样和 `release_live_hold` / `consume_live_hold` / `consume_process_hold` / `release_hold` 不会交叉等待。余量条件 `status='HELD' AND 余量 ≥ :q` 只让余量够的那次赢。跨列只在两列间挪量，可用量全程不变。
- **SCRAP_HANDOVER 用法**（04 §7.3 引用）：`q` = 剩余量（一次转完）、`op_key = CVT:{hold_id}`、`to_hold_type = 'SCRAP_PENDING'`、`reason_code = 'SCRAP'`、`source_type = 'SCRAP'`（不用 `RETURN_RECORD`）、`source_id` = **第 9 篇报损单 id**（同事务先建报损单，小赵 N2）、`operator_id = 0`、`from_hold_id` = 原 `RETURN_PENDING`。转出的 `SCRAP_PENDING` 不能人工解冻（`40933`），只能由第 9 篇报损完成或报损撤销释放，统一走 `release_scrap_hold`（§7.1.2）。必须在待回库记录 `status='OPEN'` 条件更新的同一事务里调用。
- 验证脚本两库断言：stock 40 被 `RETURN_PENDING` 冻满（available = 0）时全量转换成功（`q` = 剩余、`op_key = CVT:30`、子行 `from_hold_id = 30`）；之后 `hold_qty = 5000`、available = 0、同列明细余量 = 5000；报损明细 `source_id` 是报损单 id（9001）；重试在 PG 撞 `uq_hold_op`，在 SQLite 先撞 `hold_duplicate`；第二个关闭 rowcount = 0；人工解冻路径对 `SCRAP_PENDING` rowcount = 0（→ 40933）。A3：stock 41 上 `QUALITY` 3000、`RETURN_QC` 剩余 5000 两次全量跨列转换后冻结总量与可用量都不变。九轮：`SCRAP_PENDING` 52 凭审批回转 `RETURN_QC` 56（`from_hold_id = 52`）。本轮另加：stock 45 / hold 110（`RETURN_QC` 4000）先转 2000（`CVT:110:1`）再转 500（`CVT:110:2`），父行已释放 2500、仍 `HELD`，子行合计 2500，quality/hold/available = 1500/2500/0；同一键重放被拒；再转 3000 rowcount = 0；改 `from_hold_id` 撞 `hold_immutable`；I3e 按 `from_hold_id` 汇总仍无差异；小写 `cvt:` 被 `ck_hold_reversal_key` 拒绝。两库的 `convert_hold` 成功路径都先 `SELECT stock … ORDER BY id`，再 `SELECT stock_hold … ORDER BY id`，然后才 UPDATE/INSERT；PG 带 `FOR UPDATE`，SQLite 不带。PG 另有双会话：转换先锁 stock、停在 `pg_sleep`、再锁 `stock_hold` 并提交同列转换；`consume_live_hold` 按同一顺序锁 stock 和两条冻结后扣 1000。消耗会话在转换还停在 `pg_sleep` 时才开始，无死锁；最终 version/on_hand/hold_qty/ledger = 1/4000/4000/1，待回库已释放 3000，子行 `SCRAP_PENDING` 3000，活鲜已释放 1000。同列转换没有改库存数量。

#### 7.1.2 `release_scrap_hold`：释放报损待处置冻结

用途：第 9 篇报损单记账（`POSTED`）或撤销（`REVOKED`）时，在报损单状态条件更新的同一事务里释放 `SCRAP_PENDING`。这是 `SCRAP_PENDING` 唯一的释放路径；人工解冻接口拒绝它（40933）。

```sql
-- PG
BEGIN;   -- 调用方已开启，且已做报损单 status 条件更新
UPDATE stock_hold
   SET released_qty_milli = hold_qty_milli, status = 'RELEASED', version = version + 1, updated_at = now()
 WHERE id = :hold_id AND hold_type = 'SCRAP_PENDING' AND status = 'HELD'
   AND source_type = 'SCRAP' AND source_id = :scrap_doc_id
   -- 仅 mode = REVOKED 时追加：交接单（04 SCRAP_HANDOVER 转入）和质检不合格报损单（RETURN_QC）只进不退，不能撤销释放回可售
   -- （09 §5.2 I1/I2）；质检判错只能凭 SCRAP_MISREPORT 审批走 convert_hold 转回 RETURN_QC（§7.1.1）
   AND (:mode = 'POSTED' OR EXISTS (SELECT 1 FROM scrap_order o
                                     WHERE o.id = :scrap_doc_id AND o.source_type NOT IN ('RETURN_HANDOVER', 'RETURN_QC')))
RETURNING stock_id, hold_qty_milli AS q;   -- SCRAP_PENDING 只整条释放、从不部分释放，所以释放量 q = hold_qty_milli
-- rowcount = 0 → 40930（类型不对 / 报损单不匹配 / 已释放 / REVOKED 碰到 RETURN_HANDOVER 交接单或 RETURN_QC 质检报损单），
--   detail = {hold_id, scrap_doc_id, hold_type, status, mode}；这两类被拒时另带 scrap_source_type（'RETURN_HANDOVER' / 'RETURN_QC'）
-- REVOKED：货回可用
UPDATE stock SET hold_qty_milli = hold_qty_milli - :q, version = version + 1
 WHERE id = :stock_id AND hold_qty_milli >= :q;
-- POSTED：同一条 UPDATE 再扣 on_hand，并写 SCRAP −1 流水 + 去重键（§4.4，biz = (SCRAP, 报损单号, 行号, 1)）
UPDATE stock SET hold_qty_milli = hold_qty_milli - :q, on_hand_qty_milli = on_hand_qty_milli - :q,
       ledger_seq = ledger_seq + 1, version = version + 1
 WHERE id = :stock_id AND hold_qty_milli >= :q AND on_hand_qty_milli >= :q
RETURNING on_hand_qty_milli, ledger_seq;
COMMIT;
```

- **SQLite**：同样三条语句，`BEGIN IMMEDIATE` 拿写锁（单写者，无 FOR UPDATE）；`now()` 换 `CURRENT_TIMESTAMP`，`RETURNING` 需 3.35+（00 启动自检保证）。
- **不走可用量检查**：被冻结的量本来就不在可用量里；POSTED 只扣 `hold_qty` 与 `on_hand`，所以 `available` 不变；REVOKED 后 `available` +q。库位盘点锁不拦（与 `post_out` 不同，这部分货已不可售，报损记账不影响盘点口径，计入快照后的期间流水）。
- **交接单不能 REVOKED**：`source_type = 'RETURN_HANDOVER'` 的报损单，其 `SCRAP_PENDING` 来自待回库（04 SCRAP_HANDOVER），待回库记录已 RESOLVED 不会重开；REVOKED 释放会让破损货直接回到可售。所以 `mode = REVOKED` 时条件更新多一个 `EXISTS (… source_type <> 'RETURN_HANDOVER')`，交接单 0 行 → 40930；`POSTED` 不受影响。误报走第 10 篇异常单（09 Q8）。
- **质检不合格报损单也不能 REVOKED**（十一轮）：`source_type = 'RETURN_QC'`（第 9 篇 `ck_scr_src_type` 的取值，第 10 篇质检不合格，`source_id = inbound_line.id`）的报损单，其 `SCRAP_PENDING` 由 `convert_hold` 从 `QUALITY`/`RETURN_QC` 转入。REVOKED 释放会让质检没通过的货跳过复检直接回可售。条件更新的排除表扩为 `NOT IN ('RETURN_HANDOVER', 'RETURN_QC')`，0 行 → 40930，`detail.scrap_source_type = 'RETURN_QC'`。**质检判错只能走 `SCRAP_MISREPORT` 审批**，用 `convert_hold` 把冻结转回 `RETURN_QC`，重新质检（§7.1.1），然后由 `release_qc_hold` 释放；报损单由第 9 篇在同一事务里关闭。第 9 篇的 `trg_scr_forward` 目前只拦交接单，需要 #4 同步扩到 `RETURN_QC`；02 的 verify 测不到这一条（原因同上）。**库层强制在第 9 篇**：`scrap_order` 表归第 9 篇（PR #4），02 的 schema 里没有这张表，所以 02 的 verify 测不了这条；强制靠 ① 本条件更新（服务层），② 第 9 篇 `trg_scr_forward`（交接单不能进入 DRAFT/CANCELLED/REJECTED，报 `scrap_handover_no_revoke`），REVOKED 只会在这些迁移的同一事务里调用，迁移被拦则整个事务回滚。PR #4（`docs/09-expiry-loss` 3391682）的 verify 两库各有正反断言：交接单 REVOKED rowcount = 0，手工单 = 1。
- **与 N1 触发器兼容**：只改 `released_qty_milli/status/version/updated_at`，且沿释放方向（HELD → RELEASED，释放量增加），R1 的方向限制也不会拦。
- **库存行更新命中 0 行**（小赵 S2）：明细已释放、但 `stock` 那条 UPDATE（`hold_qty_milli >= :q`，POSTED 另加 `on_hand_qty_milli >= :q`）影响 0 行，说明 I3d 汇总与明细不平。此时**整个事务回滚**（包括明细释放、报损单状态更新），返回 500 `50010 INVARIANT_VIOLATION` 并告警，不能只回滚明细。
- **幂等**：重复调用时条件更新影响 0 行。调用方先看报损单状态：已经是 POSTED/REVOKED（同一事务里报损单状态条件更新先 0 行）→ 直接返回上次结果，不再调用本原语；POSTED 的流水另由去重键 `uq_mvk_biz_line` 兜底，不会扣两次。只有报损单状态条件更新成功、本原语却 0 行时才返回 40930（冻结与报损单不匹配，属于数据错误）。
- 验证脚本两库断言（事务内验证后回滚）：REVOKED 后 `on_hand/hold_qty/available/status = 5000/0/5000/RELEASED`；POSTED 后 `0/0/0/RELEASED`；报损单 id 不匹配（9002）rowcount = 0；非 `SCRAP_PENDING` 冻结 rowcount = 0。

#### 7.1.3 `release_qc_hold`：质检释放退货待检冻结（A3）

用途：第 10 篇退货（以及第 3 篇需要系统冻结的质检）质检通过时释放 `RETURN_QC`。签名 `(hold_id, inbound_order_id, inbound_line_id, qty, op_key)`。质检单是 `inbound_order`（冻结的 `source_id`），质检行是 `inbound_line`（合格/不合格数量在行上）。没有 `qc_line` 这张表，列名是 `qc_failed_qty_milli`，不是 `qc_rejected`。一张质检单可以分多次判定，所以是**部分释放**。不合格的部分走 `convert_hold`；人工解冻接口拒绝（40933）。

```sql
-- PG（调用方已开启事务）
-- ① 质检行累加。inbound_line 的 milli 列归第 5/10 篇，本篇只登记口径，verify 不建这张表
UPDATE inbound_line
   SET qc_passed_qty_milli = qc_passed_qty_milli + :q
 WHERE id = :inbound_line_id AND inbound_order_id = :inbound_order_id
   AND qc_passed_qty_milli + qc_failed_qty_milli + :q <= received_qty_milli;
-- ② 释放去重。op_key 由调用方传，如 QCR:{inbound_line_id}:{op_seq}；重放撞 uq_hr_op，①也撤销
INSERT INTO stock_hold_release (id, hold_id, op_key, qty_milli) VALUES (:rid, :hold_id, :op_key, :q);
-- ③ 明细：source_id 必须等于质检单头 inbound_order.id
UPDATE stock_hold
   SET released_qty_milli = released_qty_milli + :q,
       status = CASE WHEN released_qty_milli + :q = hold_qty_milli THEN 'RELEASED' ELSE 'HELD' END,
       version = version + 1, updated_at = now()
 WHERE id = :hold_id AND hold_type = 'RETURN_QC' AND status = 'HELD'
   AND source_type = 'QC' AND source_id = :inbound_order_id
   AND hold_qty_milli - released_qty_milli >= :q;   -- 0 行 → 回滚；余量不足 40905，单据不匹配 40930
-- ④ 汇总列
UPDATE stock SET quality_hold_qty_milli = quality_hold_qty_milli - :q, version = version + 1, updated_at = now()
 WHERE id = :stock_id AND quality_hold_qty_milli >= :q;      -- 0 行 → I3c 不平，回滚，50010
COMMIT;
```

- **SQLite**：同样四条语句，`BEGIN IMMEDIATE`；重放先撞 `trg_hr_no_replace`（`hold_duplicate`），与 PG 的 `uq_hr_op` 走同一个幂等分支。
- **幂等**：重放（同一 `op_key`）在 ② 撞唯一键，整个事务回滚，调用方按 `op_key` 查回已有释放行，返回原结果（200）。①②③④同一事务。
- **与 N1/R1 触发器兼容**：只改 `released_qty_milli/status/version/updated_at`，释放量只增。
- 验证脚本两库断言只覆盖库存侧 ②③④：`RETURN_QC` 挂非 `QC` 来源或 operator≠0 撞 `ck_hold_retqc`；人工解冻 rowcount = 0；释放 1000 成功；同一 `op_key` 重放后已释放 = 1000、quality_hold = 8000；`stock_hold_release` UPDATE 被拒。

#### 7.1.4 `place_hold`：加工中 / 活鲜暂养系统锁

用途：第 17 篇发料、第 18 篇锁池时冻结。只接受 `PROCESSING` 和 `LIVE_HOLD`。待报损冻结不进这个白名单，继续用 `hold(SCRAP_PENDING)`，`source_id` 是报损单 id，不是报损行 id。实现就是 `hold`，但 `operator_id` 固定为 0，并且 `POST /inventory/freeze` 与 `hold()` 的人工入口拒绝这两个类型（`40001`）。库层兜底：`operator_id <> 0` 撞 `ck_hold_process` / `ck_hold_live`。

```sql
UPDATE stock SET hold_qty_milli = hold_qty_milli + :q, version = version + 1, updated_at = now()
 WHERE id = :stock_id
   AND on_hand_qty_milli - allocated_qty_milli - reserved_qty_milli
       - quality_hold_qty_milli - hold_qty_milli >= :q;          -- 0 行 → 40904
INSERT INTO stock_hold (id, stock_id, hold_type, reason_code, source_type, source_id,
                        op_key, hold_qty_milli, released_qty_milli, status, operator_id)
VALUES (:id, :stock_id, :hold_type, :hold_type, :source_type, :source_id,
        :op_key, :q, 0, 'HELD', 0);
-- PROCESSING：source_type='PROCESS_ORDER'，op_key 前缀 PRCI:（大小写敏感）
-- LIVE_HOLD：source_type='LIVE_TANK_HOLD'，source_id=live_tank_hold.id，不强制 op_key 前缀
```

人工解冻这两类返回 `40933`，`detail = {hold_type, source_type, source_id}`。`PROCESSING` 的 `source_type` 是 `PROCESS_ORDER`；`LIVE_HOLD` 的 `source_type` 是 `LIVE_TANK_HOLD`。

#### 7.1.5 `release_hold`：释放加工中冻结（货还在）

用途：第 17 篇发料撤销。只接受 `PROCESSING`。货回到可用，不扣 `on_hand`。**完工报工不要走这条再 `post_out`**：先释放会让可用量短暂变正。完工扣料用 §7.1.6。`LIVE_HOLD` 不走本原语：整池解锁用 §7.1.7，死亡和失重用 §7.1.8。

```sql
INSERT INTO stock_hold_release (id, hold_id, op_key, qty_milli) VALUES (:rid, :hold_id, :op_key, :q);
UPDATE stock_hold
   SET released_qty_milli = released_qty_milli + :q,
       status = CASE WHEN released_qty_milli + :q = hold_qty_milli THEN 'RELEASED' ELSE 'HELD' END,
       version = version + 1, updated_at = now()
 WHERE id = :hold_id AND hold_type = 'PROCESSING' AND status = 'HELD'
   AND hold_qty_milli - released_qty_milli >= :q;    -- 0 行 → 回滚。先查冻结类型再决定错误码，见下文
UPDATE stock SET hold_qty_milli = hold_qty_milli - :q, version = version + 1, updated_at = now()
 WHERE id = :stock_id AND hold_qty_milli >= :q;      -- 0 行 → I3d 不平，回滚，50010
```

加锁顺序与其它原语相同：先 `SELECT stock … ORDER BY id FOR UPDATE`，再 `SELECT stock_hold … ORDER BY id FOR UPDATE`，然后才写释放记录和两条 UPDATE。SQLite 无 `FOR UPDATE`，语句顺序一样，靠 `BEGIN IMMEDIATE`。

明细更新 0 行时，应用层**先读 `hold_type`**，不要只看 rowcount：不是 `PROCESSING`（含 `LIVE_HOLD`）返回 **40933**；是 `PROCESSING` 但余量不够返回 **40905**。验证明细套错类型时 rowcount = 0，按这条规则映射。

`op_key` 由调用方传，重放撞 `uq_hr_op`（SQLite 撞 `hold_duplicate`）。人工 `unhold` 的 WHERE 只有 `hold_type IN ('QUALITY','MANUAL')`，对 `PROCESSING` 影响 0 行，映射为 40933。验证：对 `LIVE_HOLD` 明细套 `hold_type = 'PROCESSING'` 的条件更新，rowcount = 0。

#### 7.1.6 `consume_process_hold`：报工同步扣原料

用途：第 17 篇加工报工按产出同步扣原料。一条条件 UPDATE 同时减 `PROCESSING` 所在的 `hold_qty` 和 `on_hand`，可用量不变，中间没有“先解冻再出库”的窗口。支持部分扣，直到剩余为 0；没扣完时明细保持 `HELD`。幂等键由调用方传，写在流水去重表上。

```sql
BEGIN;
-- 0. 幂等：按 idempotency_key 等值查 stock_movement。命中就返回这条原流水
--    （id、move_qty_milli、on_hand_before、on_hand_after），任何扣减都不做。
--    全额扣完后再放同一把键时，明细余量已经是 0，若跳过这一步会落到 40905。
--    漏查时后面的插入仍撞 uq_mvk_idem，整笔回滚；那是兜底，不是正常重放路径。
SELECT id, move_qty_milli, on_hand_before_qty_milli, on_hand_after_qty_milli
  FROM stock_movement
 WHERE idempotency_key = :op_key;
-- 未命中才继续。先库存行、后冻结明细，都按 id 升序。SQLite 去掉 FOR UPDATE
SELECT id FROM stock WHERE id = :stock_id ORDER BY id FOR UPDATE;
SELECT id FROM stock_hold WHERE id = :hold_id ORDER BY id FOR UPDATE;
UPDATE stock
   SET hold_qty_milli = hold_qty_milli - :q,
       on_hand_qty_milli = on_hand_qty_milli - :q,
       ledger_seq = ledger_seq + 1, version = version + 1, updated_at = now()
 WHERE id = :stock_id AND hold_qty_milli >= :q AND on_hand_qty_milli >= :q;
UPDATE stock_hold
   SET released_qty_milli = released_qty_milli + :q,
       status = CASE WHEN released_qty_milli + :q = hold_qty_milli THEN 'RELEASED' ELSE 'HELD' END,
       version = version + 1, updated_at = now()
 WHERE id = :hold_id AND hold_type = 'PROCESSING' AND status = 'HELD'
   AND hold_qty_milli - released_qty_milli >= :q;
-- 明细 0 行：先读 hold_type，不是 PROCESSING → 40933，是 PROCESSING 但余量不够 → 40905
-- 明细够而 stock 这行 0 行，说明 I3d 不平，返回 50010
-- 流水 biz_type=PROCESS_CONSUME、direction=-1、hold_id=:hold_id
-- idempotency_key 必须是 DDL 的唯一格式 {biz_no}:{line_no}:{op_ref}:{leg}
-- 第 17 篇报工：biz_no=报工单号，line_no=领用行号，op_ref=D{op_no}（同一次报工重试 op_no 不变），leg=1
-- 例：PRC-WHSH01-20261016-000001:3:D1:1
-- 先插 stock_ledger_line 再插 key（trg_mvk_line_kind）；漏过第 0 步的重放撞 uq_mvk_idem，整笔回滚
COMMIT;
```

已释放量的对账是 I3f：`released = Σ 本行 stock_hold_release + Σ hold_id = 本行的 PROCESS_CONSUME 流水`。同一 stock 上的另一条冻结不计入。本原语不写 `stock_hold_release`，所以消耗只出现在流水一侧。

验证（stock 46，`PROCESSING` 冻满 5000，`op_key = PRCI:8801`）：扣 2000 后 on_hand/hold/available/已释放/状态/流水 = 3000/3000/0/2000/HELD/1；再扣 1000（另一把幂等键）后 = 2000/2000/0/3000/2；同一幂等键若跳过第 0 步、直接再插，撞 `uq_mvk_idem`（SQLite 报在 `stock_movement_key.idempotency_key`），回滚后仍是 2000/2000/3000/2；I3f 成立（已释放 3000 = 本行流水 3000 + 释放记录 0）；再扣 3000 rowcount = 0；对 `LIVE_HOLD` 和 `SCRAP_PENDING` 的明细更新 rowcount = 0。小写 `prci:` 与 `operator_id <> 0` 撞 `ck_hold_process`。另在 stock 52 上放两条 `PROCESSING`（130、131 各 1000），只扣 130 的 400：两条 I3f 都平；若按 stock 把 `PROCESS_CONSUME` 加总，131 会对不上。N-1：stock 53 上 `PROCESSING` 3000，`idempotency_key = PRC3:1:D1:1` 一次扣完并提交（流水 230，before/after = 3000/0，明细 RELEASED）。同一把键再调：第 0 步等值查回 230/3000/3000/0，事务里不再扣；version、在库、冻结、流水条数都不变。这时若跳过预查去做余量 UPDATE，rowcount = 0，会落到 40905，所以预查必须在扣减之前。

#### 7.1.7 `release_live_hold`：复检合格，整池解锁

用途：第 18 篇复检判定 NORMAL 时，在 `live_tank_hold` 从 `ACTIVE` 改为 `RELEASED` 的同一条条件更新里调用。按来源批量释放，不是按单条 `hold_id`。

对应关系：`live_tank_hold_id` 是锁池单 id。锁池时池内每个 stock 各 `place_hold` 一条，`stock_hold.source_type = 'LIVE_TANK_HOLD'` 且 `source_id = live_tank_hold_id`。一个锁池单对多条冻结明细。`hold_id` 是 `stock_hold.id`，和锁池单 id 不是同一行。

`release_inspection_id` 只给第 18 篇做校验和审计（同事务写 `audit_log` 和锁池单）。02 不读第 18 篇的表，本表也不加列。调用方把复检单号放进 `op_key`，例如 `LTH:{live_tank_hold_id}:{release_inspection_id}`。每条明细的去重键是 `{op_key}:{hold_id}`。

做不到一条 UPDATE。先按统一顺序加锁，再按**加锁后**的余量写释放记录，避免和 `consume_live_hold` 交错时把别人的冻结量扣掉。

```sql
BEGIN;
-- 0. 幂等：用等值查本次每条明细的 op_key（:op_key || ':' || hold_id），不用 LIKE。
--    已有释放记录就直接返回上次结果，不再写。
-- 1. 先锁库存行，按 id 升序；再锁冻结明细，按 id 升序。SQLite 去掉 FOR UPDATE
SELECT s.id FROM stock s
 WHERE s.id IN (
       SELECT h.stock_id FROM stock_hold h
        WHERE h.hold_type = 'LIVE_HOLD' AND h.source_type = 'LIVE_TANK_HOLD'
          AND h.source_id = :live_tank_hold_id AND h.status = 'HELD')
 ORDER BY s.id
   FOR UPDATE;
SELECT h.id, h.hold_qty_milli - h.released_qty_milli AS remain
  FROM stock_hold h
 WHERE h.hold_type = 'LIVE_HOLD' AND h.source_type = 'LIVE_TANK_HOLD'
   AND h.source_id = :live_tank_hold_id AND h.status = 'HELD'
 ORDER BY h.id
   FOR UPDATE;
-- 1b. 上一步锁到的 HELD 行数是 0：再跑一遍第 0 步的等值查询。
--     查到原释放就返回它。不要插入释放行，不要更新 stock，不要把 stock.version 加一。
--     并发时另一会话可能在本会话第 0 步之后才插入：等到锁时明细已经不是 HELD，
--     这时第 0 步的旧结果（0 行）作废，必须以这一次重查为准。
-- 2. 只有锁到的 HELD 行数 > 0 才写。应用为每一行发一个雪花 id（入参 release_ids），不要用 id_base + hold_id
INSERT INTO stock_hold_release (id, hold_id, op_key, qty_milli)
SELECT v.rid, h.id, :op_key || ':' || h.id, h.hold_qty_milli - h.released_qty_milli
  FROM stock_hold h
  JOIN (VALUES (:rid1, :hold1), (:rid2, :hold2)) AS v(rid, hold_id) ON v.hold_id = h.id
 WHERE h.status = 'HELD';
-- 3. 明细一次释放完（只更新本次锁到的 id）
UPDATE stock_hold
   SET released_qty_milli = hold_qty_milli, status = 'RELEASED', version = version + 1, updated_at = now()
 WHERE id IN (:hold1, :hold2) AND status = 'HELD';
-- 4. 只按本次插入的释放行 id / 冻结 id 汇总，不用 LIKE 前缀回找
UPDATE stock
   SET hold_qty_milli = hold_qty_milli - (
         SELECT COALESCE(SUM(r.qty_milli), 0)
           FROM stock_hold_release r
           JOIN stock_hold h ON h.id = r.hold_id
          WHERE h.stock_id = stock.id AND r.id IN (:rid1, :rid2)),
       version = version + 1, updated_at = now()
 WHERE id IN (SELECT stock_id FROM stock_hold WHERE id IN (:hold1, :hold2))
   AND hold_qty_milli >= (
         SELECT COALESCE(SUM(r.qty_milli), 0)
           FROM stock_hold_release r
           JOIN stock_hold h ON h.id = r.hold_id
          WHERE h.stock_id = stock.id AND r.id IN (:rid1, :rid2));
-- 行数：插入行数 = 明细更新行数；库存更新行数 = 本次 distinct stock_id。任一不等 → 回滚，50010
-- on_hand 不变，货回到可用。部分扣（死亡、失重）不走这里，走 §7.1.8
COMMIT;
```

`uq_hr_op` 仍是漏查时的兜底（SQLite 为 `hold_duplicate`），正常重放在第 0 步返回，不靠撞唯一键。verify 的库存 UPDATE 用子查询，两库同一条 SQL。上面的 `VALUES (…) AS v(rid, hold_id)` 是 PostgreSQL 写法；SQLite 3.45 不接受这个列别名，verify 两库都改写成 `SELECT :rid AS rid, :hold_id AS hid UNION ALL …`，雪花 id 仍由调用方给出。

验证：同一 `source_id` 两条明细。先锁再写。把汇总列更新写成影响 0 行，得到释放/明细/汇总 = 2/2/0，然后回滚，两条仍是 `HELD`。正路提交后三个行数都是 2，两行 `on_hand` 不变、`hold_qty` 为 0。等值再查这两条 `op_key`，已有 2 行、合计 5500，直接返回，不再写。漏查时的重放仍撞 `uq_hr_op`（SQLite 为 `hold_duplicate`）。顺序重放另测第 1b 步：stock 61 释放提交后，下一次调用第 1 步锁到 0 条 HELD，重查 `LTH:7903:9003:172` 得到释放行 193、数量 3000，`stock.version` 停在 1，释放行仍是 1 条。PG 另有并发用例：stock 60 上 `LIVE_HOLD` 3000 与 `MANUAL` 2000 并存。释放会话先按 id 锁库存行和冻结明细，再 `pg_sleep`。消耗会话确认释放会话已经停在这次睡眠里，才按同一顺序来扣 1000，因此一定会等到那把锁。消耗拿到锁时活鲜明细已经释放，整笔回滚。最终 on_hand = 5000、hold_qty = 2000，旁边的 `MANUAL` 没被扣，也没有死锁。行锁本身不进 `pg_locks`（没人等待时只写在元组头上），所以握手看的是 `pg_stat_activity` 里的 `pg_sleep`。N-2 同一把 `op_key` 的并发也用这个握手：stock 62 上 `LIVE_HOLD` 3000。释放会话持锁并停在 `pg_sleep`（此时还没插入释放行）。重放会话先等值查到 0 行，再去锁同一条库存和明细，因此等到释放会话提交之后才继续。那时 HELD 行数是 0，重查得到刚提交的那一条释放，返回它，不插入、不更新 `stock`。最终 `stock.version = 1`、释放行 1 条、数量 3000、无死锁。

#### 7.1.8 `consume_live_hold`：锁池期间死亡 / 失重，同步扣冻结和在库

用途：锁池期间的死亡登记、日失重结算。一条条件 UPDATE 同时减 `LIVE_HOLD` 所在的 `hold_qty` 和 `on_hand`，可用量不变。支持部分扣；没扣完时明细保持 `HELD`。不先 `release_hold` 再扣。

签名里的 `biz_type` 只接受 `LIVE_DEATH` 和 `LIVE_SHRINK`。其他取值返回 40001，不写库存。流水列 `stock_movement.biz_type` 写 `SCRAP`（这一列没有子类型 CHECK）。`LIVE_DEATH` 的 `source_id` = `live_death.id`；`LIVE_SHRINK` 的 `source_id` = 日失重结算行 id。`op_key` 由调用方传，并且必须是流水去重键的格式 `{biz_no}:{line_no}:D{op_no}:1`，例如 `LD-WHSH01-20261016-000001:1:D1:1`。一次调用只写一条 `direction = -1` 的流水。

```sql
BEGIN;
-- 0. 与 consume_process_hold 相同：先按 idempotency_key 等值查 stock_movement。
--    命中就返回原流水，任何扣减都不做。全额扣完后重放若跳过这一步，余量是 0，会落到 40905。
--    漏查时后面的插入仍撞 uq_mvk_idem。
SELECT id, move_qty_milli, on_hand_before_qty_milli, on_hand_after_qty_milli
  FROM stock_movement
 WHERE idempotency_key = :op_key;
-- 未命中才继续。与 release_live_hold 相同：先库存行、后冻结明细，按 id 升序。SQLite 去掉 FOR UPDATE
SELECT id FROM stock WHERE id = :stock_id ORDER BY id FOR UPDATE;
SELECT id FROM stock_hold WHERE id = :hold_id ORDER BY id FOR UPDATE;
UPDATE stock
   SET hold_qty_milli = hold_qty_milli - :q,
       on_hand_qty_milli = on_hand_qty_milli - :q,
       ledger_seq = ledger_seq + 1, version = version + 1, updated_at = now()
 WHERE id = :stock_id AND hold_qty_milli >= :q AND on_hand_qty_milli >= :q;
UPDATE stock_hold
   SET released_qty_milli = released_qty_milli + :q,
       status = CASE WHEN released_qty_milli + :q = hold_qty_milli THEN 'RELEASED' ELSE 'HELD' END,
       version = version + 1, updated_at = now()
 WHERE id = :hold_id AND hold_type = 'LIVE_HOLD' AND status = 'HELD'
   AND hold_qty_milli - released_qty_milli >= :q;
-- 明细 0 行：先读 hold_type，不是 LIVE_HOLD → 40933，是 LIVE_HOLD 但余量不够 → 40905
-- 只数或重量不够、on_hand 先不够时，应用层返回 40902（含活鲜只数不足）
-- 明细够而 stock 0 行 → I3d 不平，50010
-- 流水 biz_type=SCRAP、direction=-1、hold_id=:hold_id，idempotency_key = :op_key
-- 漏过第 0 步的重放撞 uq_mvk_idem
COMMIT;
```

对账走 I3g，按 `hold_id` 加总本行的释放记录和 `SCRAP` 流水。

验证：`LIVE_HOLD` 4000 扣 1500 后 on_hand/hold/available/已释放/状态/`direction=-1` 流水条数 = 2500/2500/0/1500/HELD/1（一次死亡只有一条 −1 流水）；同一幂等键若跳过第 0 步直接再插，撞唯一键，回滚后仍是这一条；再扣 500 后流水变成 2；I3g 成立（已释放 2000 = 本行 `SCRAP` 流水 2000 + 释放记录 0）；超量 rowcount = 0；对 `PROCESSING` 套 `hold_type = 'LIVE_HOLD'` 的更新 rowcount = 0。N-1：stock 54 上 `LIVE_HOLD` 3000，`idempotency_key = LD3:1:D1:1` 一次扣完并提交（流水 231，before/after = 3000/0）。同一把键再调：第 0 步返回 231/3000/3000/0，version 和数量不变。跳过预查的余量 UPDATE rowcount = 0，那是 40905，原语不得走到这一步。

- `biz = (biz_type, biz_no, line_no, leg)`；`src = (task_id, line_no, device_instance_id, op_seq)`，只有 PDA 作业传。
- 调用方必须已开启事务（单据状态变更与库存变更同事务）。本模块不自己提交，只在出错时抛异常。
- `post_out` 扣的是**可用量**：被预占或冻结的货不能被盘亏/报损直接扣掉。盘亏、报损要先 `release`/`unhold`，由第 8/9 篇在同一事务内编排。§12 Q4 需要第 8 篇确认。

### 7.3 FEFO 钩子（给第 4 篇的边界）

本模块**只提供数据和原子占用，不排序、不做决策**。

```python
class InventoryForAllocation(Protocol):
    def candidate_slices(self, *, warehouse_id: int, sku_id: int,
                         exclude_location_status=("LOCKED",),
                         pickable_only: bool) -> list[StockSlice]: ...
    # StockSlice = (stock_id, location_id, location_code, pick_sequence, zone_type, temp_zone,
    #               lot_id, lot_code, expiry_date, production_date, receive_date, quality_status,
    #               container_id, available_qty_milli, pickable_qty_milli, ledger_seq)
    # 数据来源 v_stock_available（已改为 *_qty_milli 列）；无锁读，结果可能过期

    def reserve_batch(self, items: list[ReserveItem], *, source: SourceRef) -> list[ReservationRef]: ...
    def allocate(self, reservation_id: int, qty_milli: int, *, op_key: str) -> ReservationRef: ...
    def release(self, reservation_id: int, qty_milli: int, *, op_key: str) -> None: ...
```

约定：

1. `candidate_slices` 是**提示**，不是承诺。第 4 篇必须假设库存在读取后随时被别人占走，以 `reserve_batch` 的结果为准（D2）。
2. 排序键、禁发期、温区、拣货位优先、整箱优先，全部在第 4 篇的 `domain/fefo.py` 纯函数里做。本模块不读 `sku.ship_min_shelf_life`。
3. `reserve_batch` 内部按 `stock_id` 升序执行，调用方不需要自己排序。
4. 越权分配（原文档 D7 `allocation_override`）的审计由第 4 篇记，本模块只记 `op_key` 和 `source`。

### 7.4 幂等语义（与总体设计一致）

- 所有 POST 必须带 `Idempotency-Key`。同 key、同请求（`req_hash` 相同）→ 返回首次响应；同 key、不同请求 → **409 `40910`，`detail.key_type = "IDEMPOTENCY_KEY"`**（00 §6.5）。
- **只缓存确定性结果**：2xx、400xx、409xx。**不缓存 422、5xx、429**：扫错库位、写锁超时、限流都是可纠正或暂时性的，同一个 key 重试要重新执行；不缓存的响应不写 `idempotency_record`（随事务回滚）。
- PDA 同一四元组、同数量 → 回放之前的结果；同一四元组、不同数量 → **409 `40910`，`detail.key_type = "PDA_OP"`**。
- `idempotency_record` 只保留 24h，PDA 离线补传可能晚于这个时间，所以本模块在中间件之下再兜两层：
  - 占用/冻结：`op_key` 唯一。重复调用撞 UK → 读回已有记录，按幂等成功返回。
  - 记账：`stock_movement_key` 的唯一键（§4.4.2）。撞约束 → 回滚，读回原流水，返回原结果。**绝不二次扣减**。

## 8. 并发与幂等

### 8.1 条件 UPDATE（不读后写）

所有判断都放进 WHERE，以 `rowcount` 为准（原文档 D2、§4.3）。各原语的 WHERE：

| 原语 | WHERE 条件 |
|---|---|
| post_out / move 来源 / hold / reserve | `on_hand − allocated − reserved − quality_hold − hold_qty ≥ :q` **AND 库位未锁定**（`biz_type ∈ {COUNT, REVERSE_PICK}` 时跳过库位锁，见下） |
| move 目标 / post_in | 库位未锁定（`biz_type ∈ {COUNT, REVERSE_PICK}` 时跳过库位锁，见下） |
| allocate | `reserved ≥ :q`（并且占用明细 `余量 ≥ :q`） |
| consume | `allocated ≥ :q AND on_hand ≥ :q` **AND 库位未锁定**（并且占用明细 `余量 ≥ :q`） |
| release / unhold | 对应列 `≥ :q`（并且明细 `余量 ≥ :q`）。人工 `unhold` 另限 `hold_type IN ('QUALITY','MANUAL')` |
| release_hold / release_qc_hold / convert_hold | 明细 `余量 ≥ :q` 且类型（及来源）匹配；`convert_hold` 跨列时另要求被减的汇总列 `≥ :q` |
| consume_process_hold / consume_live_hold | 同一条 UPDATE：`hold_qty ≥ :q AND on_hand ≥ :q`；明细分别限 `PROCESSING` / `LIVE_HOLD` 且余量 `≥ :q`。可用量不变 |
| release_live_hold | 集合更新：`source_type='LIVE_TANK_HOLD' AND source_id=:live_tank_hold_id AND status='HELD'`。①②③ 行数必须对齐，否则 50010 |

**库位锁定**统一写成 `AND EXISTS (SELECT 1 FROM location l WHERE l.id = stock.location_id AND l.status <> 'LOCKED')`，两库都支持。

**例外按 `biz_type` 判定，`post_in` 与 `post_out` 共用同一条规则**（G19）：

```sql
AND (:biz_type IN ('COUNT','REVERSE_PICK')
     OR EXISTS (SELECT 1 FROM location l WHERE l.id = stock.location_id AND l.status <> 'LOCKED'))
```

- `COUNT`：盘点本来就是在锁定状态下做的，**盘盈（`post_in`）与盘亏（`post_out`）都必须能过账**。此前例外只写在 `post_in` 语境，盘亏走的是 `post_out`，在 LOCKED 库位被 40906 拦下 → 盘亏过不了账、账实对不平（G19，长流上报）。
- `REVERSE_PICK`（撤销拣货、已拣取消回冲）：货已经在人手上，不能因盘点锁定卡在库外。
- 两者这笔入账都计入**盘点快照之后的期间流水**，第 8 篇按「实盘 − (快照 + 期间流水)」算差异，不会被算成盘盈（与 04 Q8 口径一致）。
- **其他来源仍被拦**，返回 40906：`RECEIVE`、`PUTAWAY`、`PICK`、`SHIP`、`MOVE`（两条腿）、`SCRAP` 等。
- 报损（审批后）**不走 `post_out`**，走 §7.1.2 的报损原语（该原语明确不拦库位锁）；`ADJUST` 是否需要在盘点期间放行，由第 8 篇定稿时确认（盘点关闭后解锁再过账则无需豁免，见 §12 Q13）。

两库验证脚本各 5 条断言：库位 LOCKED 时 `post_in(REVERSE_PICK)`、`post_in(COUNT)`、`post_out(COUNT)` rowcount = 1；`post_in(RECEIVE)`、`post_out(SCRAP)` rowcount = 0（→ 40906）。

PG `READ COMMITTED` 下，锁定和扣减并发时，扣减可能看到锁定前的库位状态；盘点按原文档 §5.6 扣除期间流水，所以结果仍正确。

明细表同样用条件 UPDATE：`UPDATE stock_reservation SET consumed = consumed + :q WHERE id = :rid AND reserve − consumed − released ≥ :q`。两条 UPDATE 在同一事务，任一 `rowcount = 0` 就整体回滚。

CHECK 约束是**兜底**，正常路径不该撞上。撞上即 `50010` 告警，因为这说明某条 WHERE 写漏了。验证脚本里专门有一条断言："可用量为 0 时再占 1 milli，`rowcount = 0`，不是 CHECK 报错"。

### 8.2 加锁顺序与事务边界

- 多行按 `stock_id` 升序（原文档纪律 2），`reserve_batch`、`move` 内部自动排序。
- 先锁、先改 `stock`，再锁、再改 `stock_hold`。`SELECT … FOR UPDATE` 也按 `id` 升序。`release_live_hold`、`consume_live_hold`、`consume_process_hold`、`release_hold`、`convert_hold` 都是这个顺序，避免两张表交叉等待死锁。`convert_hold` 同列不改数量，也要先锁 `stock`。SQLite 单写者，语句顺序相同，没有 `FOR UPDATE`。
- SQLite：WAL + `busy_timeout=5000` + 最多 3 次退避重试，重试只针对 `database is locked`，不针对业务失败。写事务用 `BEGIN IMMEDIATE`，避免读事务升级写事务时 `SQLITE_BUSY` 不走 busy handler。
- PG：`READ COMMITTED`。条件 UPDATE 冲突时等待前一事务，再对新版本行重判 WHERE（EvalPlanQual），语义与 SQLite 串行写一致。

### 8.3 重复过账

|---|---|---|---|
| 用户狂点 / 网络重试 | `Idempotency-Key` 中间件 | 单据行状态（第 5 篇） | `stock_movement_key` 唯一键 |
| `Idempotency-Key` 过期后重放 | — | 第 5 篇四元组 + 超拣条件更新（42214） | `uq_mvk_pda_op` |

| 同一单据行 DOC 与 PDA 两种来源各记一次 | — | 原语里的归属条件更新 | `trg_mvk_line_kind` |

### 8.4 PDA 作业与四元组的映射

PDA 业务幂等键是 00 §6.5 的四元组 `(task_id, line_no, device_instance_id, op_seq)`。映射：

| 流水 / 去重键字段 | 取值 |
|---|---|
| biz_type | `PICK` / `REVERSE_PICK` / `MOVE`（补货）等 |
| biz_no / line_no | 任务单号 / 任务行 `seq` |
| src_kind / op_no | `PDA` / 0 |
| leg | 由操作类型决定：拣货 1；移库 1 出 2 入 |
| src_task_id / src_line_no / device_instance_id / src_op_seq | 原样落四元组 |
| idempotency_key | `{biz_no}:{line_no}:P{device_instance_id}.{op_seq}:{leg}`（§4.4.2 的唯一格式） |

- **同一四元组、不同数量**：中间件和第 5 篇在去重阶段比较数量，返回 `40910`（`key_type = PDA_OP`），不会走到记账。
- 拣货消耗的占用由 `RES:{doc_no}:{line_no}:{alloc_round}:{stock_id}` 定位（§4.2），PDA 只带四元组，服务端按任务行映射到当前轮次的占用。
- 撤销拣货（`undo`）是新的 `op_seq`，写 `REVERSE_PICK +1`，不修改原流水。

**换设备实例不能重复记账**（推演）：

1. `device_instance_id` 在装机时生成，重装或换机就变；新实例的 `op_seq` 从 1 重新开始，所以四元组和旧设备**不同**，`uq_mvk_pda_op` 本身拦不住"同一个物理动作在两台设备上各报一次"。
2. 所以加一层**持有设备**：`stock_ledger_line.owner_device_instance_id` 记录该任务行当前唯一允许记账的设备实例。第 5 篇领取或改派任务时用条件更新换主（`WHERE owner_device_instance_id = :old`）；换主之前，服务端把该行已确认数量下发给新设备。
3. 记账时归属条件更新要求 `owner = :dev`，库层触发器同样校验。旧设备还在离线补传时，它已经不是持有者，补传被拒 → 走 40920/40921/40922 + 待回库（§8.5），**不扣库存**。
4. 新设备在换主之后才能记账，起点是服务端下发的已确认量；第 5 篇的超拣条件更新（`confirmed + q ≤ planned`，42214）再兜一层上限。
5. 剩余风险：拣货员在新设备上把旧设备已经报过、但服务端还没收到的数量再报一次。这不是"重复记账"，而是两次真实上报。由第 5 篇在换主时强制旧设备先同步或作废本地队列来解决，见 §12 Q10。

验证脚本断言：持有设备是 `DEV-A` 时，`DEV-B` 的记账被 `ledger_line_owner_mismatch` 拦下；PDA 行上来一条 DOC 记账同样被拦。

### 8.5 离线拒收行与"待回库"记录（表与接口归第 5 篇，第 4 篇 §7.3 定并发规则，本模块定库存口径）

PDA 离线时拣了、但任务已被改派/取消/关闭的行，服务端返回 `409`，业务码 `40920 TASK_REASSIGNED` / `40921 TASK_CANCELLED` / `40922 TASK_CLOSED`，并生成一条**待回库记录**，响应带 `returnRecordId`。

**库存口径**

1. **被拒收的行从未扣减**：服务端拒收时没有调用 `consume`，`on_hand / allocated` 不变，账面上货仍在原库位。但实物在分拣员手上，不能再被分出去。
2. **生成待回库记录时，同一事务写一条 `RETURN_PENDING` 冻结**：`hold_type = RETURN_PENDING`（独立的系统冻结类型，不是 MANUAL）、`reason_code = RETURN_PENDING`、`hold_qty` = 拒收数量、`source_type = RETURN_RECORD`、`source_id` = 待回库记录 id、`op_key = RRH:{returnRecordId}`、`operator_id = 0`。`hold_qty` 增加，所以 `available` 不含这部分，FEFO 候选分不到它。冻结同样走条件 UPDATE（`available ≥ q`）。
3. 待回库记录在四元组上唯一，冻结在 `source_id` 上唯一（`uq_hold_return`）。同一行重复补传被拒时返回已有 `returnRecordId`，**不新建记录，也不重复冻结**。
4. **确认回库**（分拣员扫原库位）：同一事务内 ①`UPDATE return_record SET status = 'CONFIRMED' WHERE id = ? AND status = 'OPEN'`，②`release_return_hold` 释放冻结（`hold_qty` 减回去，货重新可用）。**不写流水，`on_hand` 不变**。扫的不是原库位 → `422 42212`，记录保持 OPEN，冻结保留。
5. **主管处置为"就近放回"**（原库位不可用）：同一事务内，按这个顺序 ①条件更新 `WHERE status = 'OPEN'`，②**先**释放冻结，③**再**调标准 `move`（§6.5）从原库位移到目标库位：条件扣减 + 两腿 `MOVE` 流水 + 去重键。顺序不能反：冻结没释放时可用量里不含这部分，`move` 的来源条件会失败（40904）。原库位被盘点锁定或目标温区不符 → `422 42213`，整个事务回滚，记录保持 OPEN。这是待回库链路上**唯一会写流水的地方**。之后分拣员到 B 库位扫码放货，**只是物理动作，不再写流水**：移库已经在 resolve 时记过，再记就是重复记账。
6. **并发闭环**：confirm 和 resolve 只有一方的 `WHERE status = 'OPEN'` 命中。后到的一方整个事务回滚（包括它的释放冻结/move），返回 **`409 40932 RECORD_ALREADY_CLOSED`**，`detail` 带 `{status, resolution, target_location, closed_by, closed_at}`。`resolution` 取 `CONFIRMED`（扫原库位确认）/ `RETURNED_TO_ORIGINAL`（主管处置为放回原位）/ `NEARBY_PUTBACK`（就近放回），`target_location` 是货最终应在的库位。PDA 收到后视为已闭环，并提示把货放到 `target_location`。所以冻结只会被释放一次，也不会出现"已确认又移库"。`40930` 只表示通用的非法状态流转，不用于这个场景。
7. **`RETURN_PENDING`（以及 SCRAP_HANDOVER 转出的 `SCRAP_PENDING`）不能被人工解冻**：`/inventory/unfreeze` 和 `unhold` 的人工路径碰到它返回 `409 40933`；只有 4、5 两条路径在同一事务里释放它。
8. 盘点：`RETURN_PENDING` 冻结的量不参与盘点差异调整（第 8 篇负责，见 §4.3）。
9. I3d 对账：`hold_qty = Σ(MANUAL) + Σ(RETURN_PENDING) + Σ(SCRAP_PENDING) + Σ(PROCESSING) + Σ(LIVE_HOLD)` 的余量。长期不闭环的待回库由第 5 篇超时告警处理。

**冻结失败**：如果拒收时原库存行可用量已经不足（比如改派后新拣货人已经把同一批货分配走），条件 UPDATE `rowcount = 0`。建议仍然创建待回库记录，但标记"冻结未生效"并告警到主管，不阻塞 PDA。见 §12 Q9（**保持待定**）。

### 8.6 ID 与单号

按 00 总体设计 §6.1、§6.2 执行，本模块只引用：

- **ID**：雪花 ID，节点号由中心分配并写在节点配置里，**不依赖 Redis**。发号器的毫秒高水位持久化在本地表 `id_node_hwm`（每个节点号一行，条件更新预留窗口），防止重启后时钟回拨重号。检测到回拨时拒绝发号（`50302`）并告警。
- **单号**：`{单据前缀}-{仓}-{节点}-{作业日}-{序号}`，序号来自本地序列表 `numbering_segment` 的条件更新取段，两库写法相同。
- 边缘节点是否在一期启用是 00 的待定问题 **G4**（Yuri 定范围）；本篇按"每仓单写库"写，不处理多库去重。

对本模块的影响：

- 快照水位线用每行的 `ledger_seq`，不用流水 id，排序和对账都不依赖 id 大小（00 §6.1 明确 ID 不保证单调）。
- 流水的业务唯一键不含 `id`；`movement_id` 在去重表上是 PK，号段/发号异常导致的重复 id 会让事务回滚。
- 发号失败 → 原语拿不到 id → 事务不开始，返回 `50302`（时钟回拨）或 `50301`，客户端用同一个 key 重试（5xx 不缓存）。

## 9. 异常与补偿

| 场景 | 现象 | 处理 |
|---|---|---|
| 可用量不足 | `rowcount=0` | 回滚，40902/40904，上层决定缺货或重试 |
| 写冲突 SQLite `database is locked` | 超过 busy_timeout | 最多 3 次指数退避；仍失败 → 503 `50301`（不缓存），客户端用同一个 `Idempotency-Key` 重试 |
| PG 死锁 `deadlock detected` | 理论上不该出现（已升序） | 回滚 + 重试 1 次 + 告警，说明有路径没排序 |
| 撞 CHECK `ck_stock_*` | 条件写漏 | 回滚，500 `50010`，告警 |
| 撞 `append_only_violation` / `permission denied` | 有代码或脚本试图改流水 | 回滚，500 `50010`，告警（不应出现） |
| 撞 `hold_immutable` / `hold_duplicate`（非幂等重试）/ `ledger_line_immutable`（PG SQLSTATE 23514，SQLite `RAISE(ABORT)`） | 有代码或脚本试图改、删、REPLACE 冻结明细，或改单据行记账来源 | 回滚，500 `50010`，告警（不应出现）。例外：原语按 `op_key` 重试时撞 `hold_duplicate`/`uq_hold_op`，走幂等分支查回已有明细 |
| 撞 `purge_not_allowed` / `idem_duplicate`（非重放）/ `outbox_duplicate` | 有代码或脚本删未过期去重记录、未投递事件，或 REPLACE 覆盖 | 回滚，500 `50010`，告警。例外：写去重记录撞 `idem_duplicate`/23505 是正常的「键已存在」分支 |
| `release_scrap_hold(REVOKED)` 碰到 `RETURN_HANDOVER` 交接单或 `RETURN_QC` 质检不合格报损单 | 两类都只进不退（09 §5.2）；质检判错应走 `SCRAP_MISREPORT` 审批回转 `RETURN_QC`（§7.1.1） | 明细条件更新 0 行，回滚，409 `40930`，`detail` 带 `scrap_source_type`；不告警（业务拒绝） |
| `release_scrap_hold` 的 `stock` 更新 0 行 | I3d 汇总与明细不平 | 整个事务回滚，500 `50010`，告警（§7.1.2） |
| 撞 `ledger_line_owner_mismatch` | 来源或持有设备不符 | 回滚，`40930` |
| 撞流水唯一约束 | 重复过账 | 回滚，读回原流水，按成功返回；计数指标 |
| 进程崩溃/断电，事务中途 | — | 事务原子：要么余额和流水都在，要么都不在。PG 靠 WAL；SQLite 靠 WAL + `synchronous=FULL`：已提交事务不丢，**也不会出现半个事务**。未提交的事务客户端没收到 200，会用同一 key 重试；由于 `idempotency_record` 与业务写在同一库同一事务，二者一起丢或一起在，重试不会二次扣减 |
| 提交成功但响应丢失 | 客户端以为失败 | 同 key 重试 → 返回缓存响应 |
| `idempotency_record` 已过期后的重试 | 中间件放行 | 记账层唯一键兜底（§8.3） |
| 预占过期 | `expires_at` 到期 | 定时任务调用 `release`（条件 UPDATE），与正在进行的 `allocate` 竞争时只有一方成功，输的一方 40905 |
| 已拣后订单取消 | 货已离开库位 | `REVERSE_PICK` 入账回原库位或集货位（原文档 §4.2），新流水，不改旧流水 |
| 中心镜像落后、`stale_stock_policy = PAUSE`（默认，00 §9.1）| 该仓可售量不可信 | `reserve` / `allocate` / 跨仓调拨 / 波次释放触发的占用原语直接拒绝，503 `50304` STALE_STOCK_PAUSED（调用方不重试、不重取写地址，按 `/me`/心跳 `paused` 恢复），不改余额；已下发拣货任务的扣减（`consume`）、收货入账、签收相关原语照常在本仓权威库执行，最长离线 12 小时；重连后先回放 outbox 再对账，冲突写 `stock_recon_alert` 进异常队列，不自动合并 |

## 10. 权限

沿用原文档 §6.4 的三层校验，权限点名为 `{模块}.{资源}.{动作}`：

| 权限点 | 说明 | 建议角色 |
|---|---|---|
| inventory.stock.view / movement.view / reservation.view / hold.view | 只读 | 库管、主管、客服 |
| inventory.move.execute | 人工移库 | 库管 |
| inventory.hold.freeze / hold.unfreeze | 冻结 / 解冻；**解冻人 ≠ 冻结人**（职责分离，应用层校验） | 主管 |
| inventory.recon.view / recon.handle | 对账查看 / 认领、填结论 | 主管、财务 |

- 本模块的原语没有 HTTP 入口，不能被前端直接调用改 `on_hand`。盘盈盘亏、调整、报损只能经各自单据审批后由服务端调用。
- 数据权限：查询全局注入 `warehouse_id IN (user.warehouses)`。写接口校验目标 `stock.warehouse_id` 属于当前仓，**不信任请求体里的 warehouse_id**。
- 超级管理员不能做业务操作（原文档 §2.2），也就没有任何"直接改库存"的后门接口。
- `RETURN_PENDING`、`SCRAP_PENDING`、`RETURN_QC`、`PROCESSING`、`LIVE_HOLD` 是系统冻结，任何角色都不能通过人工解冻接口释放（`40933`）；SoD 规则豁免（冻结人是系统，`operator_id = 0`）。`LIVE_HOLD` 的解锁路径只有 `release_live_hold`（复检合格，整池）和 `consume_live_hold`（死亡、失重）。锁池期间出池称重同样返回 40933。
- 冻结/解冻、对账处置、就近放回都写 `audit_log`。

### 11.1 必须有的自动化测试

4. **hypothesis 状态机测试**：随机交错 reserve/allocate/consume/release/hold/unhold/move/post，每步校验不变量；最后做流水回放，结果必须等于余额。

### 附：批次可售截止日（`lot.sell_deadline`）

`lot` 的 `sell_deadline DATE`（可空）在**建批次时**由服务层写入，`= COALESCE(production_date, receive_date) + sku.sell_days`（`receive_date` 是 `DATE`，00 §6.8 第 9 条）；`sku.sell_days` 为空时为 NULL。写入之后不可改：NULL 补成日期、改早、改晚、改回 NULL 都拒。PG 触发器 `trg_lot_sell_deadline`（`IS DISTINCT FROM`）；SQLite 触发器在 `NEW.sell_deadline IS NOT OLD.sell_deadline` 时 `RAISE` `sell_deadline_immutable`（`IS NOT` 对 NULL 安全）。其余列仍可改。跨表计算不建 CHECK。超过 `sell_deadline` 的批次按 00 §6.4 走 `SELL_EXPIRED`。验证：已有批次从 NULL 补写被拒；新建批次写入成功；改早、改晚、清空被拒；只改 `remaining_life_days` 成功。

### 附：SQLite 时间列格式（小赵 S1）

`idempotency_record.created_at/expires_at`、`outbox_event.created_at/next_retry_at/sent_at` 在 SQLite 侧加 `ck_idem_ts` / `ck_outbox_ts`：必须是文本、19 位 `YYYY-MM-DD HH:MM:SS`（UTC，与 `datetime('now')` 同格式）、且是真实日期时间。CHECK 要求 `date(col)`、`time(col)` 都 `IS NOT NULL` 且与原文一致，并且 `substr(col,12,2) <= '23'`。只靠 `date()`/`time()` 回写不够：`time('2026-01-01 25:00:00')` 得到 NULL，CHECK 把 NULL 当通过；`time('… 24:00:00')` 原样返回 `24:00:00`，等号也通过。小时上限把 24 点和 25 点都拒掉。`'garbage'`、T 格式、整数、小数秒、`2026-02-30` 仍拒。PG 侧列类型是 TIMESTAMP，非法时刻在类型上就进不去，这两条只在 SQLite 断言。
