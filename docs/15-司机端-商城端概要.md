# 15 司机端、商城端 概要设计

> 编号：第 15 篇 = 司机端/商城端**前端**（本篇）；第 16 篇 = 配送与签收**后端**（小钱）。
>
> 本文为概要，详细设计见 PR #3 `docs/15-司机端-商城端.md`（合入后以其为准）。所有文档写完再开发，不分期。依据：原《WMS详细设计说明书》§2.2、§9.1、§9.3、§9.4。

## 1. 角色与场景

| 端 | 角色 | 场景 |
|---|---|---|
| 司机端 | 司机 | 接单 → 装车逐箱扫码 → 导航 → 到店签收（扫码/签名/拍照）→ 拒收/缺货登记 → 回单上传 → 周转筐/冷藏箱交接 |
| 商城端 | 客户（门店/团长） | 下单、查订单与状态、查对账、发起退货；接收缺发通知 |

## 2. 技术选型

| 端 | 选型 | 理由 |
|---|---|---|
| 司机端 | 微信小程序（原生或 Taro），`client_type=MP_DRIVER` | 司机不装 App |
| 商城端 | uni-app 或 Taro（H5 + 小程序），`client_type=H5_MALL` | 客户在微信和浏览器都下单 |

共用 §6 API，靠 `client_type`、`features`、`min_client_version` 区分；服务端兼容至少 2 个客户端版本。

## 3. 核心页面

- 司机端：任务列表、运单详情、装车扫码（扫齐才可发车）、签收（自助扫码/代签+签名+拍照/拒收选原因）、异常登记、筐箱交接。
- 商城端：商品与可售量、下单（选送达日期，WMS 计算截单顺延）、订单列表/详情、对账、退货申请。

## 4. 离线签收与补传要点

- 运单与线路任务预下载；签收结果、照片、签名本地暂存，联网补传。
- 每次签收/拒收生成一个幂等键，与记录一起持久化，补传始终复用（同第 14 篇 §9.3）。司机跨天离线是常态，24h Key TTL 不够，服务端以业务唯一键 `(waybill_no, stop_no, device_instance_id, op_seq)` 兜底，同键不同内容返回 `40910`（`key_type=POD_OP`），签收更正冲突为 `POD_CORRECT`，`4095x` 配送签收冲突码；这些业务键与码段由**第 16 篇（配送与签收后端，小钱）**定义，总体设计 §6.5 引用。本篇（第 15 篇）是司机端/商城端前端。
- 图片先上传对象存储拿 key，再提交签收；图片失败可单独重传，签收记录不重复。
- 补传冲突（运单已改派、已签收、订单已取消）标红人工处理，不静默丢弃。
- 定位只在「到达」「离开」时取；距客户地址 > 500m 要求填写说明。
- 商城端不做离线；下单带幂等键防重复下单。

## 5. 权限

- 司机只看分配给自己的运单；客户只看自己的订单与对账。
- 由后端按 token 身份强制过滤，前端隐藏不作为安全手段；按单号直接访问他人单据必须返回 403/404。
- 商城可售量走缓存表，不直接查 WMS 主表。
